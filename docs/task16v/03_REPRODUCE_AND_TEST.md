# G1 — Воспроизведение штатного upgrade с настоящим созданием данных

Обязателен **native Android upgrade test** с реальными подписанными APK24 → APK25, одинаковый package/cert, **без uninstall и без `pm clear`**. Тестовая база должна создавать объекты через обычную доступную UI/API-последовательность прежней установленной APK24; нельзя засчитать обычную SQLite fixture в качестве единственного доказательства.

## Тестовые сущности до обновления
- 3–4 собственных аудиотрека, включая записанный диктофоном через Android UI, импортированный медиафайл и одинаково названные треки с разными ID; сохранить SHA, media paths, metadata, counts.
- 2 модуля: пользовательский модуль из 3 зависимостей (название «Индукция Элмана вариант 2») и второй с индивидуальными паузами; сохранить точный граф ID и durations.
- 1 шаблон/программа с фазами и модулем, назначенные паузы.
- 2 дневниковых черновика: текстовый и мультимедийный (фото/аудио), порядок блоков, содержимое и ID.
- История сессии, личная изменённая копия, существующая экспортная капсула (если UI поддерживает), состояние очереди failed/pending; эти дополнительные данные не должны теряться.
- Не полагаться только на визуальное совпадение: manifest counts/IDs/SHA + SQLite `PRAGMA integrity_check`, file existence, checksums read-only до и после.

## Матрица жизненного цикла
A. APK24 локально без Google → создать данные через UI → штатно APK25 → запуск без sign-in → проверить.
B. APK24 с Google MASTER → APK25 → до и после refresh/повторного входа → проверить.
C. APK24 со старой ошибочной авторизацией/без сети → APK25 → офлайн/онлайн → проверить.
D. APK25 перезапуск, смена вкладок, возврат в приложение, отказ сервера/временный DNS timeout → данные НЕ становятся невидимыми.
E. Несколько версий базы, SQLite WAL/SHM, reopen/закрытие транзакций, kill во время инициализации (только в disposable тестовом окружении).
F. CLIENT-сandbox/чужой Google user НЕ получает мастерские приватные записи; recovery не обходит ACL.

При обнаружении реального destructive поведения сначала зафиксировать сценарий и вывести guard/fail closed. Не исполнять его на устройстве владельца. Запрещено «успешное» тестирование через создание новой пустой пользовательской библиотеки после сбоя; тест обязан обнаружить и остановить такой fallback.

**Выход G1:** `UPGRADE_REPRO_16V.md`, machine-readable before/after inventory (synthetic-only), native action logs/screens, точный fail→fix→pass. Если не воспроизведено, явно `NOT_REPRODUCED`, тогда готовить только диагностический кандидат после согласования, а не гарантировать исправление.
