# Дополнение №16-В · P0 · Реальные пользовательские данные не видны после MASTER24→MASTER25

**Дата:** 12.11.2026  **Проект:** «Алхимик — Сульфи»  **Статус:** немедленный STOP-SHIP / расследование и безопасное восстановление.

## Проверенный факт
Владелец сообщает: Android предложил штатное обновление существующей MASTER, он обновил APK24 до APK25 **БЕЗ удаления старого приложения**. После запуска MASTER25 пользовательские **собственные аудиотреки, созданные модули, черновики дневника** больше не отображаются. Возможно, затронуты другие личные данные. Нельзя утверждать ни физическое стирание файлов, ни сохранность, пока не установлены факты.

Это реальный **P0** и прямое опровержение достаточности synthetic-emulator gate REL-03 №16-Б. Полная приёмка №16/16-А/16-Б приостановлена до результатов настоящей диагностики и безопасного восстановления.

## Неотложный запрет
* **НЕ** предлагать владельцу `uninstall`, `Clear storage`, `Clear cache`, откат/переустановку APK24, root/flash, ручной сброс Google, повторный импорт капсул/ZIP «поверх пустой библиотеки», создание замещающих объектов или перезапись базы.
* **НЕ** запускать изменения/восстановление над физической базой пользователя, destructive schema migrations, VACUUM, GC, reset/initial bootstrap и любую запись в пользовательское хранилище без forensic-снимка, доказанной обратимости и отдельного явного согласия на пользовательские действия.
* **НЕ** подменять диагноз гипотезой «потерялась учётка». Проверить разные механизмы: локальная SQLite, файловые каталоги, фильтры/identity, ошибки миграции, переключение профиля, runtime bootstrap и визуальное отображение.
* **НЕ** выпускать новую тестовую APK, если её открытие может перезаписать старые файлы. Нет доступа к физическим данным — не заявлять, что они восстановлены.
* Не менять старый Apps Script «Сульфи — дневник», действующий Alchemist GAS6, Google ACL, signing, main, исходные APK24/25, публикационный сервер или пользователя без разрешения. Никакого нового №17.

## Приоритет результата
**P0-A — установить точную причину** по diff/кодовой истории и реальному native upgrade; **P0-B — доказать наличие/отсутствие данных без их изменения**; **P0-C — безопасная коррекция и путь восстановления**; **P0-D — регрессия на долговременных реальных объектах и подтверждение на устройстве владельца после отдельного согласования.**

Основное изменение от №16-Б: **приёмка должна проверять настоящие созданные с UI пользовательские треки, модули и дневниковые черновики**, а не только заранее вставленную synthetic SQLite fixture. Провал любого сохранения — STOP-SHIP.
