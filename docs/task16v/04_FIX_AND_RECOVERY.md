# G2 — Исправление + безопасный способ восстановить пользовательские материалы

**Приоритет №1 — существующие файлы владельца.** Не ограничиваться багфиксом «чтобы в дальнейшем не пропадало».

1. Для подтверждённой причины реализовать минимальное исправление чтения, путей, scope, миграции или ошибок стартапа. Не переинициализировать БД, если не удалось открыть старую. Никаких delete/recreate на исключении; вместо «пусто» показывать обоснованный safe error с предложением сохранить данные и связаться с разработчиком.
2. Если данные имеются и скрыты фильтром/путём — реализовать корректное, авторизованное восстановление ссылок/видимости без перемещения/перезаписи media bytes и без предоставления чужих записей другим аккаунтам. Если необходима миграция, она должна быть read-only analysis → snapshot of DB+WAL/SHM+media tree → validate digest/size → atomic staged migration → readback exact IDs/dependencies and rollback on failure. Не считать запись в новую DB без архивирования старой безопасной.
3. Если файл действительно отсутствует, доказать это по доступным read-only фактам, перечислить законные источники восстановления: конкретная экспортная капсула ZIP пользователя, локальный OS/App backup (если он реально существует), оригинальные файлы импорта. Не заявлять, что серверный каталог = бэкап всех черновиков или что капсула «подтянется автоматически».
4. Предоставить пользователю `OWNER_RECOVERY_PLAN_16V.md` с **минимальными безопасными действиями**, честно маркированным риском. До отдельного разрешения пользователя не просить его устанавливать «диагностическую» сборку на единственный телефон, не выполнять ADB pull/run-as и не импортировать капсулу. Если read-only forensic на release технически недоступен — это blocker и явный запрос способа доступа, а не спекуляция.
5. Убедиться, что повторная авторизация/выход/смена Google user не стерли local library; не «исправлять» методом глобального снятия owner-scope или скрытия защит безопасности. Изменения серверного каталога и клиента вне scope.
6. Если неисправность была в APK25, hotfix APK26 с versionCode>25 и тем же package/certificate допустима **ТОЛЬКО** после G0/G1, подтверждённого независимого теста сохранности, инвентаризации резервирования и review. Не делать automatic install владельцу; сначала представить риск и процедуру безопасного обновления.
7. Идея самостоятельного аварийного экспорта локальной базы в проверяемую пользовательскую капсулу после инвентаризации допустима как узкая recovery tooling. Не писать «автооблако» или новую систему бэкапа; отдельный бэклог.

**Выход G2:** минимальный patch, тесты миграции/отказов, rollback с сохранением байтов, `OWNER_RECOVERY_PLAN_16V.md`, `RECOVERY_LIMITATIONS_16V.md`.
