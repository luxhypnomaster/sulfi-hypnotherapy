## 1. Контракт catalogue HEAD и подготовленного snapshot

1.1. Создать версионируемый provider-neutral контракт `catalog.head` и `catalog.snapshot` либо строго совместимый adapter, не меняя существующие публичные запросы без version negotiation. Схема: schemaVersion, scope, catalogRevision, snapshotId, snapshotHash, createdAt, content metadata; отдельная область прав/диарийной конфигурации. Только сервер определяет ACL и доступные материалы. Секреты, чужие персональные данные, private readers, локальный read-state в публичный snapshot не включать.
1.2. Одна неизменяемая snapshot-редакция публикуется как доступный HEAD только после того, как полная запись проверена. На отказах/прерывании предыдущая опубликованная редакция остаётся читаемой. Уважать настоящий GAS6 storage/LockService/Drive model — нельзя выдавать SQL-транзакцию за имеющуюся возможность. Синхронизация изменений не должна запускать полный scan Drive и rebuild на каждом `HEAD` GET.
1.3. Пакетные метаданные, contentId/revision, versioned deps, real receipts/requestId, concurrent publish без lost update. При невозможности обеспечить atomic HEAD на текущем adapter представить **tested isolated implementation and migration plan** без live изменения. Не тратить время на несанкционированную production публикацию.
1.4. Если существующий GAS6 protocol не позволяет прямую доставку, сделать self-contained injectable provider-neutral adapter + automated Node tests, demo fixtures и соотносимый diff. Не маскировать mock результат как live GAS PASS. Файловые байты (аудио, картинки) вне snapshot; ссылки защищены сервером, а не скрытием UI.
1.5. Сохранить старые legacy endpoints и данные; о невозможности связать новую схему без production изменения сообщить как dependency/blocked, затем перейти к независимым блокам ниже.

## 2. Дешёвая локальная синхронизация catalogue

2.1. Клиент при открытии отображает lastGood локальный каталог, затем асинхронно получает лёгкий HEAD с scope/version/checksum. Совпадение редакции => нет запроса полного каталога. Несовпадение => получить snapshot, проверить schema/scope/hash и необходимые зависимости, атомарно применить локально и выдать один CatalogChanged.
2.2. Процесс interruption/timeout/503/hash failure/older response: не очищать current, хранить lastGood, retry с backoff; не копить вечные IN_FLIGHT; account isolation. Новый scope/другая Google учётка не наследуют приватные данные прежней. Визуальная панель без мерцания. Не скачивать все аудио при одной проверке метаданных.
2.3. Использовать существующую durable SQLite очередь №18, coalesce множественные refresh intents per account/scope. Не создавать parallel queue или новый Android worker без доказанного необходимости. Не путать операцию и сетевую попытку, истечение session lease не удаляет подтверждённые файлы и receipts.
2.4. Перенос между хостингами: никакой жёстко кодированной зависимости от Supabase Cloud/TatNet; URL и transport behind backend adapter; политику auth оставлять existing Google до отдельного задания. Все счетчики/данные о пользователях не включать в публичный HEAD.

## 3. Локальная дневниковая витрина / карусель на текущем Flutter HOME

3.1. Использовать действующую верхнюю область главного баннера, сохраняя фактическую высоту, координаты планшета, стикеров, нижних кнопок и общий художественный стиль. Рисунок S-M-DIARY-HOME-001 — только про внутреннюю иерархию содержимого публикации, НЕ эталон пропорций экрана. Никакого глобального редизайна.
3.2. В существующем контейнере два состояния: фирменная заставка и публикация. Публикация содержит компактный title, выразительный shortMessage, прямоугольную первую картинку строго справа без искажения, реальные +N для дополнительных элементов; если есть собственное аудио — фирменную Play-спираль, запускающую первую аудиодорожку в СУЩЕСТВУЮЩЕМ скользящем мини-плеере. Tap на title/message/image открывает полный дневник. Play не открывает дневник и не отмечает read.
3.3. DEFAULTS: splash 3 сек; entry 7 сек; заставка после всего полного круга; high:normal = 1:1; pinned EveryNth = 3 отдельной настройкой, не подменять её priority ratio. Два режима splash: after full cycle или between posts. Таймеры редактируются как целые 1..60 секунд. Показывать все допущенные актуальные НЕПРОЧИТАННЫЕ entries, без искусственного потолка; read pinned/high не может оставаться в карусели. Пустая очередь => постоянная заставка без периодического перезапуска. Отсутствующая группа high/normal не создаёт пустых слотов. Несколько pinned справедливо чередуются; N=1 не может голоданием вытеснять остальные.
3.4. Local isRead keyed by account+entryId+activationCycleId; нет server per-user reader-state/diary audio analytics. У существующего legacy `readerState` push/pull может быть личный исторический прогресс — сначала прочесть и обеспечить миграцию/защиту, только затем выключать запись в публичную целевую модель. Не удалять legacy записи без backup или явной user approval. Если невозможно безопасно мигрировать, включить compatibility adapter с `new local-only mode` default безопасно и отдельно зафиксировать оставшийся blocker, не останавливать весь №20.
3.5. Read semantics latest S-M-DIARY-HOME-001 v1.1: без собственных аудиоблоков конец последней страницы становится read, а полностью помещающаяся одностраничная запись требует осознанного «Дочитано». Если собственное DiaryMedia.audio имеется, после достижения конца последней страницы доступна кнопка «Отметить прочитанным» независимо от прослушивания. ContentLink на каталожное аудио не считается diary audio и не влияет на прочтение. Прочтение не закрывает открытую запись и не останавливает аудио. Тихая коррекция content revision не сбрасывает прочтение; только явный reannounce меняет activationCycleId и возвращает unread.
3.6. Собственные diary media должны получить verified local readiness с существующим downloaded-asset/work queue, без насильственной загрузки связанных catalog ContentLink. Новая готовая публикация перестраивает локальную очередь на конце текущего слайда, в одном coalesced update; если текущая недействительна из-за revoke/expiry, убрать немедленно. Без per-slide HTTP и без прерывания текущей гипносессии/аудиоплеера.
3.7. Авторский предпросмотр как существующая публикация: не помечать read, не изменять очередь, не публиковать, не запускать живой таймер. Если готового editor preview нет — приоритет корректности core carousel, отдельный OPEN UI с тестами, не придумывать макеты.

## 4. MASTER → Управление → Публикации и витрина → Настройки витрины

4.1. Использовать существующий утверждённый стикер «Управление» только MASTER. В CLIENT вкладки нет. Не передвигать или перекрашивать HOME за пределами согласованной композиции. В актуальной S-D-ADM-001 v2.2 для блока «Публикации и витрина» приняты две вкладки — «Публикации» и «Настройки витрины». В текущем №20 реализуется только минимальная безопасная настройка витрины и совместимость с существующим редактором публикаций; полная семистрочная панель «Управление» и остальные административные разделы остаются ВНЕ №20.
4.2. Внутри существующего визуального языка дать минимальный редактируемый экран параметров витрины: два таймера 1..60 с (default 3 и 7), режим заставки (default after full circle), ratio high/normal (default 1:1), pinnedEveryNth (default N=3), раздельный draft/saved/published и индикация ошибки/отката. Недоопределённые максимумы ratio и N не выдавать за согласованные UX-решения; валидировать технически безопасные значения и в отчёте указать proposed bounds. Предпросмотр статичен.
4.3. Настройки публикуются только после server-side role check и versioned commit; CLIENT читает одну applied конфигурацию вместе с проверенным snapshot, затем работает локально. Нет admin mutation по локальному `edition=master`, email или скрытой кнопке. При отсутствии согласованного production API — реализовать UI + isolated staging/mock admin adapter + тесты, но НЕ включать фальшивую кнопку якобы действующего live-save.

Отдельные новые функции «Состояние сервера» и «Резервные копии» (S-D-ADM-001 REQ-ADM-022…027) являются УТВЕРЖДЁННЫМ НАПРАВЛЕНИЕМ, но не частью production подключения в этом срочном №20: backend provider ещё не выбран. Можно создать только provider-neutral интерфейсы и тестовые fake-адаптеры БЕЗ лживых цифр и псевдоуспешных бэкапов, если не ухудшает главные блоки; их полноценную реализацию оставить на отдельный этап после выбора инфраструктуры.

## 5. Обязательные проверки

5.1. Unit/Node: server HEAD unchanged, failed publish before pointer flip, corrupt snapshot, repeat requestId, concurrent publishers, per-scope/ACL/withdrawn, 100 objects/20 shared modules, no locked secret, reader-state not leaked.
5.2. Flutter: six refresh intents => one logical sync; equal HEAD => no full fetch; different scope A/B; network/offline, bad hash, resume, atomic local swap, client package-specific scope; no old SessionRun modification.
5.3. Diary: 3/7 and 1/60 boundary, pinned 3 and 4, high/normal fairness, empty/one/many, read pinned excluded, reannounce vs quiet edit, read single page, own audio vs ContentLink, no reader audio telemetry, media availability, coalesced slide-end refresh, revoke immediate, no per-slide network. Phone 9:16 geometry preserved, Play uses existing player.
5.4. Regression: №18 native background transfers; existing Google sign-in/roles; signed in/out; author drafts; audio/wav/cover retention; upgrades without SQLite/media loss; 2 distinct accounts; no client admin, server denies owner-hint escalation.
5.5. Flutter analyze/test, Node tests, relevant Kotlin tests, compile/APK only if runner/tools available. CI billing blocked != tested PASS. Real physical owner phone, real Google accounts and live GAS6 are separate status gates; don't claim simulated tests as phone proof.
