# CODEX: АВТОНОМНОЕ ВЫПОЛНЕНИЕ БЕЗ ПАУЗ НА НЕБЛОКИРУЮЩИХ СБОЯХ

Это прямое указание владельца для №20. Не останавливаться на каждом несостоявшемся промежуточном тесте, неподтверждённой конфигурации или требовании отдельной команды продолжения. Продолжать все безопасные, независимые, уже разрешённые работы из пакета.

1. Открывая задачу, создай `reports/task20/PROGRESS.md` с минипланом tracks и status. После любого содержательного checkpoint обновляй файл, сохраняй коммит. Не проси confirmation для перехода между разрешёнными tracks.
2. После успешного этапа делай узкий тест; после блока — две осмысленно отличающиеся попытки устранения с новой диагностикой. Не повторяй один и тот же failure просто чтобы «израсходовать токены». Если исправление невозможно, запиши точный stack/log/причину/файлы и `BLOCKED_ENV` / `BLOCKED_OWNER` / `FAIL_IMPL`, затем переключись на другой трек.
3. При CI billing blocked, Google staging credentials unavailable, Android emulator/KVM missing, Gradle OOM — НЕ ПРЕКРАЩАЙ весь task. Продолжай изолированные Node/Dart/JVM, подготовь исчерпывающие live/manual QA checklists, подготовь alternate CI/manual runner instructions. Не меняй платёжные настройки, лимиты, аккаунты, проект и токены.
4. Если обновление каталога требует неразрешённого живого GAS deploy — завершай код в изолированной ветке, injected adapter, тестируемый diff, а live update пометь BLOCKED_OWNER. Затем работай над локальной синхронизацией и дневником. Не выдавай partial mock за live.
5. Если бизнес-правило/UX недоопределено — реализуй доказанные принципы и безопасные default из SDD, покажи OPEN-решение и не делай произвольный необратимый выбор. Продолжи другие разрешённые части. Предметы OPEN в конце, не вопросы пользователю посреди текущего запуска.
6. Не жди ответов пользователя для чтения repo, тестов, чистых патчей на branch, внутренней документации, демонстрационных fixtures и CI без платных изменений. Предполётные проверки — не permission prompts.
7. Если опасное действие требует согласия — останови ТОЛЬКО это действие; нельзя молча делать production deploy, main merge, destructive migration, Google OAuth/GAS ACL mutation, project billing changes, remote user-data cleanup, overwrite protected media, security bypass. Остальные tracks продолжаются.
8. Сохраняй защищённые старые функции, делай backward-compatible adapters, feature flags по умолчанию безопасные, no data loss. Regression FAIL не является сигналом отключить тест или удалить исходные данные. Откат должен быть возможен до новой успешно проверенной версии.
9. В конце зафиксируй ровно: что готово в source; какие tests реально PASS, SKIP, FAIL, NOT_RUN; где необходимы manual proof/owner consent; ссылки branch/PR/commit; ресурсы/лимиты только по наблюдаемым фактам.
10. Цель владельца — интенсивное полезное использование имеющихся примерно 65 процентов недельного лимита. Приоритет — прогресс в работающем коде и доказательствах, а не процент расхода сам по себе. Если исчерпаны безопасные tracks, завершай честно.
