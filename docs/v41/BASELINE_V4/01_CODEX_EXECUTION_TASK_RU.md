# КОПИРУЕМОЕ ЗАДАНИЕ ДЛЯ CODEX — СУЛЬФИ v4.0

Работай над **существующим Flutter/Android-приложением «Сульфи — Самогипноз»** в подключённом репозитории. Это комплексная доработка работающего проекта, не создание нового приложения и не прототип из статичных картинок. Прилагай настоящий код, миграции, тесты и UI, а не только рекомендации. Предыдущие версии ТЗ (v2, v3.0, v3.1) отменены там, где противоречат этому пакету.

## Сначала прочитай

1. Файлы репозитория: `AGENTS.md`, `SPEC.md`, `BACKLOG.md`, `VERSIONING.md` и существующий код/модели/тесты.
2. `00_README_RU.md` — статус, границы, порядок чтения и приоритеты.
3. `02_UNIFIED_SPEC_V4_RU.md` — **полное единое нормативное ТЗ**.
4. `03_DATA_MIGRATION_IMPLEMENTATION_RU.md` — модели, сценарии миграции, статусы, порядок.
5. `04_RECORDER_STATE_MACHINE_RU.md` — **реальный диктофон**, кнопки, permissions, сохранение.
6. `05_ACCEPTANCE_TESTS_RU.md` — проверяемая приёмка.
7. `06_FINAL_AUDIT_AND_DECISIONS_RU.md` — решения, снятые противоречия, невыдуманные допущения.
8. `07_ASSET_MANIFEST_RU.md` и графику в `assets/`.

## Функциональные принципы, которые нельзя нарушать

- Структура **Фаза → Модуль → Трек**; временные элементы «Тишина»/«Самостоятельная работа» и паузы ДО. Убрать публичный термин «блок» для одиночного трека.
- 10 стандартных фаз, но не 10 обязательных аудиоэтапов. Любой тип фазы может повторяться. Один `ModuleDefinition` может быть добавлен **сколько угодно раз даже в одну и ту же фазу**, каждое применение независимо. Не создавать отдельную кнопку «Дублировать модуль».
- Каталог модулей пользователь формирует **уже сейчас**: при импорте MP3 или записи своего трека можно назначить существующий, создать новый или оставить трек без модуля. Любой модуль доступен любой фазе; рекомендации — только сортировка.
- Не строить сейчас конкретные шаблоны «Разведка», «Курение», «Похудение» или фиктивный аудиоконтент. Готовые авторские MP3 появятся позже. Первое открытие может показать пустой черновик и предложение импортировать.
- Текущий черновик, шаблон и история независимы. Не изменять исходный шаблон, когда редактируют экземпляр модуля/трек. Мигрировать и сохранить всю существующую библиотеку, пользовательские файлы и события.
- Главный экран: референс `assets/screens/01_MAIN_APPROVED.png`, но **сохранить обязательную карточку активного шаблона**. Сверху компактная строка с номером, полными датой и днём недели, временем/темой; структура на всю ширину и всё свободное место до шаблона; CTA **`НАЧАТЬ ТРАНСФОРМАЦИЮ`**. Четыре пункта внизу: **`Записаться к мастеру`** (спираль), `Библиотека`, `Шаблоны`, `История`. Микрофонную кнопку с главной убрать.
- По первой кнопке — диалог Telegram/email с внешним открытием и локально конфигурируемыми настоящими URL/email. Пока адреса неизвестны — НЕ выдумывать.
- Диктофон обязательно **реализовать, не оставить пустой экран**. Утверждённый референс `assets/screens/02_RECORDER_APPROVED.png`: сверху параметры, снизу запись с большой спиралью, четыре действия Delete/Preview/Pause/Finish, отдельная центральная спираль `Начать/Продолжить`, в самом низу **«Отмена» слева / «Сохранить трек» справа**. `Завершить` останавливает захват, `Сохранить` записывает в библиотеку и выбранный модуль; не путать.
- Экран выполнения сессии: убрать текущую путаницу между паузой, прерыванием и выходом. Воспроизведение реального расписания в фоне при блокировке телефона, MediaSession, audio focus, контроль остановки, события и восстановление. Находящиеся в очереди паузы/тишина не должны зависеть от видимого Flutter-виджета.
- История: компактный журнал, день недели, дата, номер, длительность, статус; из записи `Повторить сессию` и `Создать шаблон из сессии` по **полному сохранённому плану запуска**, не только воспроизведённой части.
- Иконка приложения: спираль без текста, launcher-label **«Сульфи»**. Брендинг из приложенных файлов, не генерировать новый логотип наугад.

## Процесс реализации

**Шаг 0 — обследование/план:** изучить текущую архитектуру и реальный уровень готовности диктофона, background playback, Module/Track и хранилища. Зафиксировать несовместимости и дать краткий технический план в отчёте / PR description. Не обещать результаты до проверки.

**Шаг 1 — модель и безопасная миграция:** тестовые фикстуры старых данных, новые сущности/адаптер, стабильные ID, `ModuleDefinition`/`ModuleInstance`, `PhaseType`/`PhaseInstance`, точный ordered timeline. Уплотнить legacy только сохраняя исходный порядок/паузы, не сносить media.

**Шаг 2 — импорт и управление модулями:** форма MP3 с тегами, create/attach/none, отсутствие жёсткой связки `фаза=модуль`, независимость каталога/экземпляра и корректный поиск.

**Шаг 3 — структура, паузы, шаблоны:** 10 фаз, повторения, выбор модулей, отдельные треки, золотой редактор задержек и верный total; UI без «блоков».

**Шаг 4 — реальный диктофон:** разрешение, start/pause/resume/finish/preview/delete/save, экран по референсу, связывание записи с модулем, устойчивое локальное хранение.

**Шаг 5 — главная, контакты, навигация, иконки:** полноширинный список, дата+день недели, «Начать трансформацию», «Записаться к мастеру», Telegram/email, Android adaptive icon.

**Шаг 6 — выполнение/фон/история:** service-backed timeline, понятная панель выполнения, pause/resume/freeWork/exit/interrupt, корректные статусы/checkpoint; компактный журнал, повтор/создание шаблона, frozenPlan и timezone.

**Шаг 7 — приёмка:** выполнить/написать автоматизированные тесты из `05_ACCEPTANCE_TESTS_RU.md`; `flutter analyze`, `flutter test`, `flutter build apk` при наличии SDK, проверить ui на скриншотах и особенно фоновый звук/диктофон на физическом Android, если доступен. Отдельно указать НЕПРОВЕРЕННОЕ.

Можно делать **несколько последовательных PR**, чтобы после каждого приложение собиралось. Все PR в `develop` из отдельных feature branches. **`main` не менять и не переписывать историю git.** При нехватке ресурсов реализовать максимально возможный полный вертикальный срез, явно перечислить недоделанное; не выдавать макет за работающий код.
