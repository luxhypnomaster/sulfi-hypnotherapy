# СУЛЬФИ v4.1 — ГОТОВОЕ ЗАДАНИЕ ДЛЯ CODEX

Работай **в существующем подключённом Flutter/Android-репозитории приложения «Сульфи — Самогипноз»**. Не создавай новый проект, не замещай приложение скриншотами, не изменяй `main` и не удаляй пользовательские медиа/данные. Цель — сделать максимально возможный проверенный объём изменений **по утверждённым требованиям**, не обращаясь ко мне за уже решёнными продуктовыми вопросами.

## Обязательное чтение
1. Изучи `AGENTS.md`, `SPEC.md`, `BACKLOG.md`, `VERSIONING.md`, `pubspec.yaml` и фактический код репозитория, если эти файлы существуют.
2. Прочитай `00_START_HERE_RU.md`, `05_PRIORITY_CONFLICTS_AND_PHASES_RU.md`.
3. Прочитай весь `BASELINE_V4/` начиная с `00_README_RU.md`, `02_UNIFIED_SPEC_V4_RU.md`, `03_DATA_MIGRATION_IMPLEMENTATION_RU.md`, `04_RECORDER_STATE_MACHINE_RU.md`, `05_ACCEPTANCE_TESTS_RU.md`. Его базовое задание `01_CODEX_EXECUTION_TASK_RU.md` остаётся в силе, кроме замен, перечисленных здесь.
4. Прочитай `02_PLAYER_FINAL_SPEC_V4_1_RU.md` и `03_PLAYER_TESTS_RU.md`; используй **именно** `assets/PLAYER_FINAL_APPROVED_9x16.png` как утверждённый художественный референс активного плеера.
5. `04_DIARY_DECISIONS_DEFERRED_RU.md` изучи как будущий контракт, но **не реализуй дневник и его облако в эту ночную итерацию**, если это потребует нового дизайна/архитектурных предположений.

## Порядок самостоятельной работы
**0. Аудит до изменений:** определи реально работающие и отсутствующие требования, текущую git-ветку, зависимости, состояние тестов, schema/storage, background audio, recorder, player. Составь `reports/00_AUDIT.md` с таблицей DONE / PARTIAL / MISSING / BLOCKED для v4.0 и v4.1. Не пересоздавай готовые реализации.

**1. Безопасность и модель:** обеспечь snapshot/frozenPlan, независимые Phase/Module/Track instances, стабильные ID, корректную миграцию legacy без потери локальных записей; добавь тесты. Если уже готово — не переписывай ради переписывания.

**2. Конструктор/библиотека/паузы:** доведи неработающие части v4: создание и редактирование модулей, импорт/диктофон, повторы, свободные треки, длительности, рекурсивные планы, golden pause editor. Не выдумывай авторские записи.

**3. Воспроизведение и финальный плеер:** сначала проверь service-backed execution/background/checkpoint и события, затем реализуй новый живой UI строго по `02_PLAYER_FINAL_SPEC_V4_1_RU.md`, согласуй с v4 exit semantics. Никаких имитаций аудио или таймеров. Проверяй весь диапазон от нулевого прогресса до завершения.

**4. Остальное v4:** текущая главная, диктофон, история, контакты/ярлык — исправляй по результатам аудита. Держи приложение собираемым после каждого вертикального этапа.

**5. Тесты и отчёт:** запускай доступные `flutter analyze`, `flutter test`, `flutter build apk --debug` и релевантные интеграционные/миграционные проверки. Если Flutter SDK/телефона нет — явно отметить NOT TESTED, не симулировать результат. Проверку background/audio focus/микрофона на физическом Android не объявлять PASS без устройства.

## Как работать по времени и зависимостям
- Начни сразу после чтения материалов, не ограничивайся только планом или аудитом; переходи к коду, если репозиторий доступен.
- Работай безопасными небольшими commits/PR в существующем workflow (изолированная feature-ветка от `develop`, когда она существует). Не пушь в `main`; не используй `reset --hard`, force-push, автоматическое удаление личных аудиофайлов.
- Если объём превышает доступную сессию, доведи до **законченного рабочего вертикального среза** с тестами, затем переходи к следующему. Не оставляй специально сломанную сборку ради большого недоделанного UI.
- Не вноси собственные продуктовые изменения вместо отсутствующего решения. Если можно безопасно применить разумную инженерную реализацию без изменения контракта, делай и документируй; иначе пометь BLOCKED и продолжи другие готовые задачи.
- `Professional` навигация по касанию шкалы колбы — **НЕ в MVP**, только архитектурное примечание для будущей версии.
- Не использовать последние ошибочные коллажи и посторонний дневник. Единственный новый UI asset — `assets/PLAYER_FINAL_APPROVED_9x16.png`.

## Требования к итоговому результату
1. Список коммитов / изменённых файлов и доказательство наличия рабочего кода.
2. Какие задачи реализованы и какие остались частичными; фактический аудит относительно v4.0 + v4.1.
3. Результат `flutter analyze`, `flutter test`, `flutter build apk --debug` с реальным выводом или честным NOT TESTED.
4. Результат миграции и сохранности данных, воспроизведения, таймеров и фоновой работы.
5. Скриншот нового экрана на реальном Flutter-render, если среда позволяет (не фотографию референса, выданную за работающий экран).
6. Путь к реальному APK, если сборка выполнена.
7. Файл отчёта по шаблону `06_DELIVERY_REPORT_TEMPLATE_RU.md`.

**Приоритет неизменных решений:** Фаза → Модуль → Трек; десять типов фаз, допускаются повторы; модуль из каталога в сессии — независимый экземпляр; MP3 и реальная запись с микрофона; безопасный запуск/прерывание/выход; никакого фиктивного контента. Участки v4, не затронутые дополнением v4.1, действуют полностью.
