# Физическая приёмка, ограничения доступа и критерий успеха

## Почему прежняя физическая потеря не должна блокировать ВЕЧНО

Владелец прямо сообщил: прежние test modules/audio/diary drafts не являются уникальными и исходники медиа лежат отдельно на его телефоне. Операция восстановления этих старых тестовых объектов **исключена из №16-Г**. Это осознанно ограниченная приёмка будущей сохранности, а не заявление «потери не было». Старый root cause по устройству остаётся UNKNOWN.

## Контрольный набор на MASTER25 (создаётся только владельцем)

- Три тестовых аудиотрека, в том числе два с одинаковым отображаемым названием, но разными bytes/ID; при возможности записанный в приложении тестовый голос + локально импортированные файлы.
- Два пользовательских модуля: один включает три трека, второй паузу и один общий трек. Одна сохранённая «программа» (пока old UI «шаблон») с фазами/модулями/пауза; тестовый сеанс и история.
- Два черновика дневника: текстовый и мультимедийный, если действующая авторизация позволяет. Не включать в synthetic native PASS если через реальный UI не созданы.
- Контрольные названия/количество/состав/время, сохранность фото/аудио и внешний оригинал фиксируются скриншотом/заметкой самого владельца; секреты/подлинный личный контент не загружать в Git/отчёты.

**Риск:** текущая APK25 имеет неустранённые storage risks. Владелец может использовать только заменимые тестовые материалы, никаких уникальных записей. Не нужно делать импорт/переустановку/очистку ради диагностики. Из теста можно выйти, если заметны признаки повторной потери.

## После безопасной controlled сборки candidate26

1. Android update поверх MASTER25 с тем же package и подписью, версия строго больше; не удалять/не очищать данные. При конфликте package/signature — STOP, не предлагать uninstall.
2. Проверить старые тестовые треки, модули, программу, черновики, историю, текущую сессию после первого запуска и cold restart. Модуль ссылается на те же track IDs, длительности/порядок совпадают.
3. Проверить приложение в airplane mode: оригинальные локальные файлы и воспроизведение; не импортировать автоматически ничего из сети.
4. Google MASTER и CLIENT: вход, закрытие/повторный вход приложения, auth restore/refresh, разграничение ролей, отсутствие повторной аутентификации без необходимости.
5. MASTER загрузка модуля с тремя оригинальными треками, подтверждение server commit в каталоге; отдельная программа, включающая модуль; ContentLink дневника; повторное редактирование текста публикации не перезаливает аудио; обложка сохраняется.
6. CLIENT видит каталог, устанавливает модуль и программу с правильными зависимостями; общие аудио не дублируются. Офлайн проигрывание — слышимость человеком и корректное переключение треков.
7. Одна проверка Wi-Fi/mobile/DNS обрыва на заменимых файлах; итог server response, queue retry, отсутствие дубликатов, ясный error/status. Никаких скрытых Google токенов в логах.
8. Итог: owner PASS/PARTIAL/BLOCKED по каждой цепочке. Если для live нужен reviewed GAS deploy — отдельное явное решение владельца до него.

## Приёмочный принцип

Формулировки «без потери локальных данных», «авторизация стабильна», «публикация работает» и «CLIENT офлайн» подтверждаются только соответствующей физической приёмкой. Flutter unit PASS, контролируемый эмулятор и signed APK не заменяют owner proof. Старые данные мастерского телефона не обещаем восстановить; новые создаваемые тесты должны переживать upgrade, иначе STOP-SHIP.
