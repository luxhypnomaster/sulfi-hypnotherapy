СУЛЬФИ — ЗАДАНИЕ №5 (ОКОНЧАТЕЛЬНАЯ РЕДАКЦИЯ ДЛЯ CODEX)
Корректирующая сборка после пользовательской приёмки APK №4
Дата: 07.11.2026
Статус: ИСПОЛНЕНИЕ. Прежде чем менять код, проверить реальное состояние репозитория и уже реализованных требований; ни один пункт не считать выполненным без подтверждения кодом/тестом.

0. ПРИНЦИП ИСПОЛНЕНИЯ И ГРАНИЦЫ

0.1. Прочитать AGENTS.md и правила репозитория. Установить действительную рабочую ветку/HEAD и наличие незакоммиченного кода. НЕ возвращаться к старой версии ради удобства. Сопоставить реализацию и отчёт по Заданию №4 с конкретными воспроизведёнными пользователем дефектами. Для требований №4, выполненных по факту, делать регрессионную проверку, но НЕ переписывать готовый код.
0.2. Фокус №5: (А) реальный баг обновления APK, (Б) запись из дневника, (В) архитектура режимов и категорий, (Г) новая карточка истории и навигация после сессии. Остальное — проверка и минимальные исправления регрессий №4. Не вносить новые сценарии авторизации, удалённые серверы, ИИ, медицинский контур Alchemica и прочее из стратегического проекта.
0.3. НЕ МЕНЯТЬ принятые визуальные решения главной страницы, библиотеки с поиском, множественным выбором и фильтрами, жёлтого карандаша изменённого шаблона, настройки паузы с двумя механическими маховиками, уже соответствующего эскизу диктофона (если соответствие подтверждено), уже работающей отдельной прокрутки и автоподсветки списка активной сессии. Разрешены только узко обоснованные интеграции.
0.4. Продолжить существующие контракты капсул, переносимых ID, связанных модулей и архивных сессий из ТЗ №4; проверять совместимость, не переосмыслять их как новые подсистемы. Личные данные и ресурсы не удалять и не сбрасывать ради прохождения теста. Резервная копия должна быть проверяема ДО потенциально разрушающей миграции.
0.5. Результат: исходный код, воспроизводимая сборка APK, тесты/диагностика и отчёт PASS/FAIL/NOT RUN по каждому сценарию. Нельзя заявлять о тесте, который не выполнен.

1. P0. ОБНОВЛЕНИЕ APK ПОВЕРХ УСТАНОВЛЕННОЙ ВЕРСИИ

1.1. Наблюдение пользователя: APK №4 снова не устанавливается как обновление предыдущего APK; пришлось удалить старую установку. Значит задача №4 по бесшовному обновлению НЕ ПОДТВЕРЖДЕНА и фактически не достигнута в тестируемом сценарии.
1.2. Диагностировать конкретную причину с помощью имеющихся APK №3 и №4 (если доступны), `apksigner verify --print-certs`, `aapt`/`apkanalyzer`, Gradle-конфигурации applicationId, versionCode, versionName, signingConfig и adb install -r / PackageManager кода ошибки. Для APK №5 закрепить неизменный package ID, возрастающий versionCode и воспроизводимый канал подписи. НЕ выдавать смену versionCode за доказанное исправление несовместимого сертификата. Не класть ключи/пароли в репозиторий.
1.3. Если на устройстве была APK с ключом, которым текущая среда не владеет, прямое обновление этой установки может быть невозможно; сообщить об этом прямо. Настроить неизменную подпись для будущих выпусков (№5 → №6). Провести измеримый тест №4 → №5, если реально доступна подписанная №4 с тем же ключом; иначе показать непроверенные предпосылки и повторяемый пользовательский маршрут диагностики. Не удалять чужие данные.
1.4. Миграции формата данных и проверка инсталлятора — РАЗНЫЕ процессы. Даже успешно установившаяся APK должна сохранить пользовательские аудио, шаблоны, модули, истории, дневники и ID после первого запуска. Отдельный тест на синтетических данных и восстановление из капсулы.

2. P0. ДНЕВНИК: НЕ СОХРАНЯЕТСЯ АУДИОФРАГМЕНТ

2.1. Подтверждённый воспроизводимый дефект №4: «Дневник → Добавить блок → Аудио → Записать», пользователь записывает звук (в том числе во время редактирования текста), останавливает, видит запись с длительностью, но при сохранении получает ошибку «Не удалось записать или сохранить. Дубль не удалён: проверьте микрофон и свободное место». Удаление дубля и повторная запись дают ошибку вновь. При записи аудио через структуру сессии сценарий работает. Не диагностировать это как неисправность микрофона без проверки.
2.2. Изучить сохранение временного файла, разрешения, контекст вызова рекордера, маршрутизацию возвращаемого результата, ссылки в редакторе дневника, операции копирования/переименования, ошибки в логах. Воспроизвести именно контекст дневника; выделить точную техническую причину, а не переписать всё аудиохранилище.
2.3. ОДИН звуковой движок/рекордер, ДВА контекста использования:
  а) «Библиотечный трек»: утверждённая полная форма — название, описание, категория, теги, добавить в модуль, фирменный крупный микрофон со спиралью, таймер, иконки управления, сохранение в библиотеку. Сохранять эскиз.
  б) «Аудиовложение дневника»: упрощённая форма того же рекордера — необязательное название (автоподстановка), блок записи, время, управление, «Отмена» и «Добавить в дневник». НЕТ категорий, тегов, описания, выбора модуля. НЕ РЕГИСТРИРОВАТЬ в «Общих», «Установках» и «Моих».
2.4. Дневниковое аудио — логическая сущность `diary attachment` со стабильным ID и связью с конкретным аудиоблоком страницы. Можно использовать общее приватное хранилище с отдельным namespace/каталогом (например diary audio), НЕ строить второй независимый аудиодвижок. Импортированный из телефона аудиофрагмент дневника должен идти тем же маршрутом прикрепления, без регистрации трека библиотеки. Включать вложения в капсулу, корректно восстанавливать связи. Оригинал аудио на телефоне не менять.
2.5. Запись сначала во временный файл → проверить, что звук реально сохранён/декодируем → атомарно прикрепить к блоку дневника. Отмена, ошибка и недостаток места не должны уничтожать черновик, текст, картинки или ссылку на предыдущий фрагмент. Если имя отсутствует, создавать понятное автоматическое. Проверить последующее воспроизведение и повторное открытие дневника; запись не должна появляться в библиотеке.
2.6. Не изменять утверждённый мультимедийный редактор дневника (отступы, навигация, пагинация, текст/изображения) за пределами формы записи и связывания нового аудиоблока. Публикацию через непроверенный Google Apps Script не трогать.

3. P1. АВТОРСКИЙ И КЛИЕНТСКИЙ РЕЖИМЫ; КАТЕГОРИИ

3.1. Подтверждённый баг №4: при добавлении обычного аудио выбор категории «Мои» сохраняет трек в «Мои»; «Установки» действительно перемещает его в «Установки»; при выборе «Общие» запись фактически остаётся в «Мои» (при том, что «Общие» предлагается в выпадающем списке). Проверить сохранение и чтение поля категории, фильтры и возможное ограничение системных ресурсов. Сохранить существующий UI библиотеки.
3.2. Ввести отдельные поля: категория/раздел отображения (`Общие`, `Установки`, `Мои`) и происхождение/владение аудио (`bundled/system`, `user-created`/`imported`); они не заменяют друг друга. Авторское помещение пользовательской записи в «Общие» НЕ превращает её в системную и не исключает из капсулы; обновление приложения не вправе перетирать её.
3.3. Концепция двух режимов одной Sulfi: `AUTHOR` — создание и изменение авторского контента, в том числе распределение треков по всем категориям, модулей и базовых материалов; `CLIENT` — ПОЛНОЦЕННЫЙ самогипноз: выбор/настройка сессий, создание и правка собственных шаблонов и личных модулей, личные записи, дневник, воспроизведение, история, капсулы. В CLIENT запрещены операции изменения/публикации именно ПОСТАВЛЯЕМЫХ авторских ресурсов, но не самостоятельные конструкторские возможности пользователя. Клиент вправе создавать личные записи и шаблоны, но не выдавать их за поставляемые общие элементы. Не делать клиентский режим демонстрационным.
3.4. Для тестовой/авторской сборки переключение режима в существующих настройках (не на утверждённой главной), без потери данных и пересоздания библиотек. Для выпуска отдельной полноценной клиентской APK переключателя режимов нет, режим фиксируется конфигурацией сборки и операции авторства действительно недоступны на уровне сервисов/сохранения, а не только скрыты кнопки.
3.5. Предусмотреть централизованную проверку возможностей пользователя/сборки (capabilities) и ясное поведение всех точек входа: библиотека, выбор аудио, редактирование библиотечного модуля и личного модуля, поставляемого и личного шаблона. Не скрывать у клиента конструктор личных сессий/шаблонов. Не требовать новой системы удалённой авторизации, многопользовательского сервера или отдельной профессиональной Alchemica в этом ТЗ. Все старые пользовательские записи мигрировать с сохранением их категории, где это возможно. Сохранять категории, выбранные пользователем сознательно.
3.6. Важный сценарий: в режиме AUTHOR импортировать файл и выбрать «Общие» → файл виден в «Общие», не остаётся ошибочно в «Мои»; после переключения в CLIENT файл виден для использования, но авторское редактирование запрещено. Это ещё личный по происхождению материал, он входит в капсулу, не становится автоматически базовым ресурсом для всех устройств. В CLIENT импорт личного трека по правилам UX доступен в личной категории, не в «Общие».
3.7. При изменении источников/режимов не ломать связанные определения модулей и жёлтый индикатор несохранённого шаблона. Если для технической реализации нужно менять прежнюю схему лицензирования/прав, вынести отдельным блокером, не выполнять молча.

4. P1. НОВАЯ КАРТОЧКА ИСТОРИИ СЕССИИ И НАВИГАЦИЯ

4.1. Подтверждённая обратная связь: после завершения рабочая сессия закрывается, приложение отправляет в общий список истории. Это не аварийный дефект, но пользователь утвердил более полезный сценарий: после завершения штатно сохранять запись и открывать СРАЗУ карточку ТОЛЬКО ЧТО завершённой сессии внутри раздела «История», не общий список. И при естественном окончании, и при явном досрочном завершении. Карточка должна открываться по устойчивому ID только что сохранённого прогона; без дублей при повторном открытии. Назад — в список истории. Сохранение/навигация должны быть устойчивы к возврату/перезапуску приложения.
4.2. Дизайн карточки: эталон — присланный пользователем РАННИЙ строгий рамочный план сессии ДО введения колбы. Строгая тёмная кожа/неон/золото и компактная иерархия. Не переносить колбу и большое игровое представление активной сессии в историю. Приоритет — читаемость и наглядность. Приложенный скриншот `Референсы/История_ранний_структурный_эскиз.png` — РЕФЕРЕНС КОМПОНОВКИ, не точное требование копирования подписей/состояний, поскольку эскиз создан для другого экрана.
4.3. СВЕРХУ ПЕРЕД структурой: история / номер конкретного сеанса, название проведённой сессии, фактическая дата и время начала/завершения (при доступности), длительность, исходное имя шаблона, итоговый статус (`завершена`/`прервана`), короткие сводные числа по выполненным фазам/трекам при наличии фактов. После метаданных — ТЕКСТОВОЕ ОПИСАНИЕ/ЗАМЕТКА. Не подменять заметку пользователя описанием исходного шаблона: можно показать оба поля с правильными подписями. Существующую заметку хранить в истории, редактировать только явно и не менять исходный снимок исполняемой структуры. Если заметки конкретной сессии пока нет, обеспечить необязательное текстовое поле для её добавления в карточке с сохранением отдельно от неизменяемой структуры; пустое описание не подменять придуманным текстом.
4.4. НИЖЕ описания — ВСЕГДА ПОЛНОСТЬЮ РАЗВЁРНУТЫЙ блок «План и ход сессии» / «Структура сессии». Без аккордеона, toggle, автоматического сворачивания фаз, кликов для раскрытия модулей и дополнительных состояний раскрытия. Структура идёт последней после заголовка/метаданных/текстового описания, поэтому человеку, которому она не нужна, достаточно до неё не прокручивать. Если нужна — сразу видит все детали. Единая вертикальная прокрутка всей карточки. Сохранить фазовую иерархию: фазы в отдельных заметных рамках, внутри модули (только при достоверных исторических границах), прямые аудиотреки, паузы и подпункты. Для паузы — миниатюра утверждённого символа драконьего глаза из часов, без ненужной анимации и без переделки настроечных часов. Это обзор реальных событий, не свободно редактируемый текущий план. АВТОСВОРАЧИВАНИЕ завершённых фаз допускается только в плеере АКТИВНОЙ сессии, не в её истории.
4.5. СТАТУСЫ: зелёная галочка — элемент полностью завершён по достоверному факту проигрывания/событий; нейтральный/серый — не начат, неизвестен или ещё не подтверждён; красный крестик/прерывание — только когда явное событие прерывания/ошибки существует; значок пропуска/перемотки — ТОЛЬКО если в сохранённом журнале есть однозначный соответствующий факт. НЕЛЬЗЯ ретроспективно выводить ручную перемотку из процента прослушивания или «не зелёного» статуса. НЕ добавлять сейчас телеметрию перемоток, порог прослушивания или запрет seek. Достиг конца трека даже после seek → завершённый трек, как сейчас. Если лог №4 недостаточен, сначала показывать безопасные статусы `завершён / не завершён / неизвестно`, возможное расширение фактов предложить отдельно.
4.6. Карточка должна опираться на НЕИЗМЕНЯЕМЫЙ snapshot исходного плана и отдельные фактические события из истории №4, а не на текущие библиотечные определения модулей. Если состав исходного шаблона изменился, история всё равно отображается как была проведена. Не сохранять заново историю при открытии карточки; не изменять ранее проведённую сессию при изменениях действующего шаблона. Заголовки модулей отображать, если исторический snapshot содержит достоверные границы; если снимок намеренно раскрыт до фаз и треков и границы недоступны — НЕ выдумывать имена/связи, либо использовать уже хранимые необязательные метаданные происхождения без влияния на fingerprint. Состояние «выполнено» должно агрегироваться только из сохранённых детей.
4.7. ДВЕ КНОПКИ внизу карточки:
   • «Повторить сессию»: проверить существование/отпечаток актуального шаблона и исходного исторического плана по №4. Если совпадает раскрытая структура — обычный текущий шаблон. Если не совпадает или удалён — временный архивный план из сохранённых фаз, прямых треков и пауз БЕЗ модулей. Если аудио отсутствует/изменилось — НЕ стартовать как точный повтор, показать список и путь «Пересобрать сессию». Предупреждать о несохранённом текущем плане перед заменой. Новый запуск — новая запись в истории. Стартовать воспроизведение согласно согласованному действию.
   • «Открыть в редакторе» (или краткая подпись «В редактор»): открыть историческую ИСПОЛНЯЕМУЮ структуру как новый временный НЕСОХРАНЁННЫЙ план для дальнейшего редактирования/сохранения как нового шаблона. Исходная история и исходный шаблон не изменяются. Если есть достоверные и неизменённые библиотечные модули с совпадающей структурой и ID, можно восстановить ссылки; при неизвестных/устаревших модулях раскрыть до прямых треков/пауз, сохраняя фазы, без создания ложных библиотечных модулей. Если аудио отсутствует — показать элементы-проблемы и дать пересобрать с явной заменой/удалением, без тихих подстановок. Перед заменой существующего несохранённого плана получить подтверждение.
4.8. НИКОГДА не создавать из истории постоянный шаблон/модули автоматически. Кнопка «В редактор» не является «повторить воспроизведение» и не должна автоматически запускать аудио. Не добавлять в №5 профессиональные карты пациентов, врачебные аннотации и AI-конвейер — это будущая Alchemica, текущая карточка лишь пригодна для дальнейшего расширения.
4.9. Приёмка: полная сессия, прерванная сессия, частичная фаза, пауза, seek почти до конца с естественным завершением, отсутствие/замена аудио, изменённый/удалённый исходный шаблон, несохранённый текущий план, повторная навигация в карточку; реальное восстановление «В редактор» и сохранение НОВОГО шаблона. Проверить отсутствие дублей истории. Проверить, что структура и вложенные элементы изначально ВИДИМЫ, без кликов по заголовкам/аккордеонам; на длинной сессии прокручивается ВСЯ карточка; два нижних действия доступны после структуры, не перекрывают содержимое. Открытие подробной карточки из общего списка истории должно давать тот же экран.

4.10. Зафиксировать источники данных карточки: ID конкретного прогона, исходные метаданные шаблона, времена выполнения, неизменяемый снимок структуры, независимые события исполнения, отдельное редактируемое описание/заметки. Если старые записи не содержат части метаданных, показывать «нет данных», не симулировать результаты. Не добавлять новые полные копии аудиофайлов в историю; сохранить правила капсулы №4.

5. P2. РЕГРЕССИОННАЯ ПРОВЕРКА ЗАДАНИЯ №4 (ИСПРАВЛЯТЬ ТОЛЬКО ЕСЛИ НЕ ГОТОВО)

5.1. Универсальный мини-плеер предпрослушивания на главной, в структуре сессии, редакторе модуля и библиотеке. Визуальный и функциональный эталон — уже работающий в библиотеке. Проблема на старой APK: Play запускал звук, но не открывал плашку, а иконка строки не переходила в Pause. Проверить APK №4: если исправлено — только тест; если нет — подключить общий компонент и синхронизированный контроллер, не четыре копии. Не вмешивать preview в движок основной активной сессии.
5.2. Активная сессия: проверить, что зелёные полностью завершённые фазы автоматически сворачиваются как модули, НЕ сворачиваются недоигранные/будущие; часы показывают Play/Pause выше времени без стрелок внутри кольцевого seek; внешние кнопки работают; три таймера компактно справа; золотой процент возле колбы; нет дубля полосы прогресса; список прокручивается внутри экрана и удерживает активный элемент. Эти требования уже были в №4, не повторять рефакторинг при прохождении.
5.3. Диктофон обычного трека: сверить с утверждённым художественным эскизом (крупный микрофон + спираль, отдельные поля, иконки, композиция). Не допускать упрощённой формы дневника вместо полной формы библиотеки. Если в №4 уже доведён — не трогать, кроме параметризации контекста вызова.
5.4. Диарист: режим автора/читателя и базовые мультимедийные блоки редактора приняты; не переделывать их ради нового аудио. Капсулы: проверить экспорт, восстановление и сохранность аудио вложений; работающую реализацию не переделывать.
5.5. Связанные модули: «Сохранить изменения» (тот же ID + связи обновляются в незапущенных планах/шаблонах), «Сохранить как новый» (новый независимый ID), неизменная история — всё из №4. Проверить smoke-тесты; при корректной реализации не трогать.

6. ПРИЁМКА, ОТЧЁТ И КРИТЕРИИ ГОТОВНОСТИ

6.1. Для P0 обязательны причинно подтверждённое исправление или документированный блокер (например, недоступный подписывающий ключ). Формулировка «починил обновление» без сравнения подписей/теста не принимается. Для аудио дневника — end-to-end на реальном устройстве/эмуляторе: запись 10–15 сек во время написания текста → сохранить → воспроизвести → закрыть и открыть редактор → аудио на месте, библиотека не загрязнилась; повторная запись, отмена, импорт с телефона, восстановление капсулы.
6.2. Для режимов: переключить AUTHOR/CLIENT в тестовой сборке; права на все операции; импорт в «Общие» в AUTHOR, видимость и происхождение, импорт в «Мои» в CLIENT; категория «Установки» остаётся рабочей; в CLIENT создание/редактирование собственного шаблона и модуля работает, а изменение поставляемого авторского ресурса запрещено; сохранность при переключении и капсуле. Клиентская релизная сборка без переключателя и авторских операций должна быть отдельной конфигурацией, но не требовать обязательной публикации второго APK сейчас, если это не входит в инфраструктуру сборок.
6.3. Для истории: UI-скриншоты актуальной APK, сценарии из 4.9, проверка точности snapshot и результат обеих кнопок, отсутствие ложных значков перемотки, правильный маршрут по завершении/назад, единая запись истории. Дать отдельно исходную схему данных, миграционные тесты и решения при старом журнале, где нет детальных событий.
6.4. Все тесты помечать PASS / FAIL / NOT RUN / BLOCKED с причиной. `flutter analyze`, `flutter test`, `flutter build apk`, актуальные версии Flutter/Android и reproducible build, сертификаты fingerprint без раскрытия ключей. Отчёт: git HEAD/ветка, diff stat, перечень исправленных дефектов №4, скриншоты, конфигурация подписи и ограничения, путь/размер APK, оставшиеся дефекты. Никаких секретов или реальных личных аудио в репозитории/отчёте.
6.5. STOP: если изменение данных требует удаления пользовательской базы, выпуск с несовместимым ключом без безопасного маршрута, потеря истории, модуля или аудио, либо затрагивает уже утверждённый внешний вид без причины — остановить соответствующий участок, подробно описать блокер, выполнять независимые безопасные части. Не заявлять общую приёмку при FAIL P0.
