Если название уже содержит слово «изменено», метку всё равно не путать с именем. Для названия отличающегося шаблона на стартовом экране — тот же UX (жёлтая метка, отдельная фуксия+курсив у названия). ## 2. Экспорт/импорт материалов как понятный пользовательский путь (K-012–K-016)
- В действующем Flutter экспорт трека/модуля/шаблона сохраняет **content package** через SAF и текущий capsule формат, НЕ «резервную копию». Исправить исключительно подписи: «Экспортировать материал», «Экспортировать модуль» и т.п., полную резервную капсулу сохранить отдельной явно названной операцией.
- Имя **выборочного ZIP** по умолчанию строго `Sulfi_exp_<transliterated_title>_DD.MM.YY.zip`, например `Sulfi_exp_Glubokoe_rasslablenie_09.11.26.zip`. Для track/module/template единый формат. Поле `originalTitle` в manifest остаётся в UTF-8 на исходном языке. Транслитерация русских букв в латиницу (не автоматический английский перевод), нормализация Unicode, пробелы→`_`, удаление опасных/недопустимых файловых символов и traversal, ограничение длины, `Untitled` для пустого. Если SAF позволяет пользователю выбрать конфликт — не перезаписывать молча, предложить rename/suffix. Дата = локальная дата устройства при экспорте; экспорт не зависит от языка интерфейса. `DD.MM.YY` — human-facing имя, в manifest timestamp всегда ISO-8601 UTC.
- Полный backup оставлять форматом **`Sulfi_backup_DD.MM.YY.zip`**, вне `Sulfi_exp_*`; полный формат (scope full) и выборочный экспорт логически различаются даже если оба ZIP/manifest. Не менять capsule/schema ради имени и не нарушать legacy import.
- Сделать понятную **видимую кнопку «Импортировать ZIP»** там, где пользователь реально ищет импорт: в Library/настройках либо открываемом существующем каталоге; использовать уже реализованный `LocalCatalogSource`/select-file→preview→resolve dependencies→install. Сохранять название «Локальный каталог материалов», если экран уже принят; не создавать второй installer. Системное Android «Извлечь» не является импортом в Сульфи. После успешного импорта показать что установлено, где найти материал, без дубликатов.
- Отдельный backup restore должен сопровождаться явным предупреждением о масштабах и конфликтных данных. Не выдавать выборочный ZIP за полную резервную копию.
- Тесты: реальный ZIP с 3 аудио+паузы; точный порядок/длительности/хеши; единичная установка в ПУСТУЮ тестовую БД, повтор без дублей, конфликт старой/новой версии не перезаписывает; corrupt ZIP/path traversal/нет места безопасно отказывают; экран импорта доступен на мобильных размерах.

## 3. Закрыть критические PARTIAL №14 — exact revisions / хранилище аудио (VER-02/CAT-03/CAT-04/EXP-08/CAT-06)
- Не принимать существующий `content_revisions` как гарантию хранения всех аудиобайтов: runtime по-прежнему обращается к legacy `audioAssetId`, а `UNIQUE(filePath)` не отражает владение blobs разными ревизиями.
- Спроектировать и реализовать **только additive, проверяемую миграцию** SQLite и файлов с `BlobKey(digest) → physical file` и явными revision/dependency/ownership ссылками либо эквивалентным безопасным механизмом. Все readers (import, preview, runtime session, library, history snapshot, cleanup, deletion) должны использовать exact audio revision когда она известна. Если unknown legacy ref — сохранять текущий валидный путь без вымышленной revision.
- Сценарий v1 с байтами A → v2 с байтами B: они сосуществуют; старая сессия продолжает читать A, новая B. Нельзя менять AudioAsset для прежнего логического ID так, чтобы история начала ссылаться на B. Удаление/cleanup не вправе удалить blob, на который ещё ссылается хотя бы одна сохраняемая ревизия/история/план, а duplicate digest разных ID хранится физически один раз **если это безопасно подтверждено тестами**.
- Installer: dry-run exact missing hashes и отдельная оценка staging+reserve; cross-ID dedup, metadata-only/different-version conflicts, conflict preview, отмена/rollback, повтор после аварии. `SIGKILL`/crash harness отдельного процесса и reopening SQLite, безопасная recovery marker/journal policy. Не утверждать испытания power-loss без аппаратного теста.
- Migration на копии заполненной schema9 из №14 (история с вложениями, audio, собственные записи, шаблоны, diary, status, reader state), идемпотентный повторный upgrade, legacy capsule 6/7/8/9 и invalid manifests, rollback/forward-correction. Никогда не DROP/RENAME старые пользовательские таблицы без специально одобренной миграции и миграционного доказательства.
- При обнаружении риска потери данных: **не делать рискованную миграцию наугад**. Завершить безопасные фазы, зафиксировать точный blocker и тестовый воспроизводимый fixture; GATE №3 отметить PARTIAL. Переход к серверу запрещён для содержания, которое предполагает одновременное сохранение разных аудиоревизий и не может это гарантировать.

## 4. Дневник — завершённый офлайн локальный функционал до сервера (K-001–K-007, K-018/K-022/K-023 по контракту)
- Сохранить существующий мультимедийный редактор/читатель и личные медиа. Не создавать дневник с нуля. Раздельные: авторский draft/publication revision/cycle; локальное read state каждого читателя; contentLinks в extra от №14. Не помечать «прочитано» от простого открытия.
- Категории: принятую базовую шестёрку (точные русские названия из `DIARY_AND_CLIENT.md`); приоритет, срочность, read и publication status — разные независимые поля.
- Прочтение: текст+изображения → достижение последней страницы; аудио → полное реальное прослушивание, pause/seek не равен завершению; смешанная запись требует обоих условий. Перепрослушивание, возврат, частичное состояние и повторное открытие не должны необоснованно ставить read. User state локальный на устройстве, по reader ID/цикл публикации, не общедоступное поле.
- Ротация на главном: актуальные **непрочитанные**, приоритетная→обычная→приоритетная; новая актуальная выходит первой по согласованному правилу; прочитанные не вращаются, остаются в архиве. Когда непрочитанных нет — существующая заставка Сульфи, не новый дизайн. Реальный медийный макет главной K-008 не утверждён; не изобретать новую отрисовку — использовать уже существующий компонент и описать UI blocker отдельно, если он не может показать контент.
- Тихая правка опубликованной записи не создаёт новый цикл read; явная «Показать снова как новое» создаёт новый `activationCycleId` без повторной загрузки unchanged media. Ручное закрытие, истечение срока (UTC timestamp + timezone display), комбинированное: более раннее событие. Закрытие → убрать из активного/непрочитанного/витрины, но не удалять данные.
- Авторский ContentLink picker: по точной выбранной ревизии трека/модуля/шаблона, записывает структуру, а не свободный URL или медиафайл; в offline черновике сохраняется, при отсутствии установленного материала читатель увидит честное «недоступно» либо выберет локальный пакет. Никогда не отправлять новые поля в существующий несовместимый live API.

Если отсутствует принятый K-008, не имитировать готовность — выдать UI_BLOCKER K-008 и полноценно протестировать остальную логику.
- Подготовить локальный `DiffPlan` для будущей инкрементальной публикации: старые asset digest повторно не загружать, изменение title/priority/readCycle → 0 бинарных uploads, новая картинка → только один новый asset, порядок блоков → manifest only. - Аудировать уже существующее `--dart-define=SULFI_EDITION=client` и `test/task5_client_build_test.dart` из №14. Не создавать второй независимый кодовый продукт. Одна кодовая база и версионированные модели, **два режима сборки** для проверки на двух телефонах: Author/test и Client/test. Пользователь может установить их на разные устройства, желательно с separate package ID только для клиентской test edition **после проверки текущего Gradle/flavor workflow и сохранения существующей установки**. Не менять подписанный production ID и не публиковать client-flavor под тем же авторским доступом/секретом.

Локальный switch «Автор/Клиент» является UX-переключателем, НЕ серверной ролью/доказательством прав. Реальные права доступа обязательно проверить на сервере в следующем ТЗ.
- Клиент может безопасно открывать опубликованные fixture-записи, локально отмечать прочтение, получать ContentLink, переходить к каталогу/установке, использовать свои аудиосессии/историю и сохранять личный контент. В отсутствии сервера — локальные seed/mock fixtures. Не показывать фиктивный «опубликовано в облако».
- Контрактное e2e на двух независимых temporary stores/profiles: Автор создаёт запись+один прикреплённый файл/ссылку → `FakeProvider` публикует immutable manifest → Клиент читает → полная read-state по правилам → получает контент → повторная публикация с новым cycle возвращает unread; без кросс-утечки приватных авторских данных. Тот же сценарий должен быть воспроизводим для будущего реального server provider без замены клиентских доменных моделей.
