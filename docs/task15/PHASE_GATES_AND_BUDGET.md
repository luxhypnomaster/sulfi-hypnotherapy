# ЭТАПЫ, ПРОХОДЫ, ЛИМИТЫ — НЕ СЖИГАТЬ НА ПОВТОРНОМ ЧТЕНИИ

Идея владельца — стартовать после обновления 5-часового окна и получить максимально много полезной работы. Это **не значит**, что одна модель способна гарантированно сделать всё за один прогон. ТЗ исполняется без параллельных агентов, по последовательным checkpoint.

| Этап | Приоритет | Проверяемый результат | Условие перехода |
| --- | --- | --- | --- |
| G0 | P0 | Git baseline №14, branch, schema9, тесты/права, REPORT baseline15 | `PROGRESS.md` + commit только при изменении |
| G1 | P0 | bug две копии; жёлтое «(Изменено)»; домашний щит | targeted test/UI PNG + commit |
| G2 | P0 | экспорт с понятным именем; видимый импорт ZIP; backup отдельно | реальный roundtrip fake files + commit |
| G3 | P0/high risk | exact audio revision blobs, safe migration/rollback, crash tests | populated migration + targeted tests, либо честный PARTIAL |
| G4 | P0 | diary local categories/read/reannounce/expiry + ContentLink author UI | state tests + widget/snapshots + commit |
| G5 | P0 | client edition, no author privileges, two-store fake provider e2e | 2 CI builds/contract tests + commit |
| G6 | P0 | server handoff schemas, API conformance, final CI/APK + report | full PASS or declared blockers |

**Порядок:** G0→G1→G2→G3→G4→G5→G6. Если G3 требует сложной unsafe миграции, изолировать незавершённую работу в отдельной ветке/коммите или отложить без половинчатой миграции, записать blocker, продолжать G4–G5 без декларации серверной готовности точных аудиоревизий. Ни одна недоказанная технология не должна быть помечена DONE.

## После КАЖДОГО этапа, до перехода
1. Закончить атомарные изменения и целевые тесты, `git status` прочитать.
2. Сохранить отдельный git commit (если есть changes). Обновить `PROGRESS.md`: gate, HEAD, passed IDs, partial IDs, blockers, что читать дальше, конкретная следующая команда.
3. Писать отчёт кратко, не перепроверять всю историю проекта, не перезапускать окружение только из-за смены этапа. Полный 379+ Flutter suite — на G0 базовой сверке при необходимости, после рискованной миграции G3 и один раз на G6.
4. При достижении лимита: остановиться без риска, оставить branch+commits+`PROGRESS.md`; НЕ начинать новый чат Codex с тем же полным ZIP для повторной работы, возобновить прежнюю задачу по `RESUME_INSTRUCTIONS.md`.
5. Запрещено `flutter clean`, удалять app data/проекты, создавать второй импортёр, массово переписывать UI или пытаться обойти заблокированный Apps Script, если это не доказанная необходимость.

## Ограничение ресурсного риска
При недостатке времени/лимитов приоритет реальной ценности: G1+G2 (видимые исправления) раньше больших архитектурных рефакторингов; G3 — самый рискованный и может продолжаться в следующем окне; затем дневник/клиент и будущий сервер. Но в итоговом отчёте **полный комплект G0–G6** оценивается честно, а не объявляется выполненным при остановке.
