0. ПРЕДМЕТ И ВАЖНОЕ УТОЧНЕНИЕ
РЕШЕНИЕ ВЛАДЕЛЬЦА (ОБЯЗАТЕЛЬНО): во ВСЕХ направлениях пользовательских обменов, которые контролируют Android-приложения MASTER и CLIENT (загрузка и выгрузка), transfer продолжается после сворачивания приложения, переключения на другой экран/приложение и блокировки дисплея. Пользователь не должен держать Сульфи открытой ради 10–20 МБ аудио или скачивания пакета материалов. При допустимом ограничении ОС задача безопасно сохраняется и возобновляется. Слово «фон» не означает безусловной вечной работы вопреки ограничениям Android, ручному Force Stop, выходу из аккаунта или политике сети. Но штатное сворачивание НЕ должно превращаться в USER_PAUSED.
Это не косметическая правка двух кнопок. Нужен полноценный Android-aware durable transfer executor с подтверждёнными байтами, идемпотентными commit/receipt, жизненным циклом и системными уведомлениями. Одинаковые инженерные гарантии в MASTER и CLIENT, общий модуль/контракт при фактически разных APK/ролях. Запретить псевдо-фикс, снимающий lifecycle guard, оставляющий передачу на Flutter Activity/Isolate, обречённую при suspend.
СТАТУС: ТЗ создано для Codex, сам код №18 ещё НЕ реализован. Код текущей APK27/ветки №17, сервер GAS6 и пользовательские данные пока не изменены. Выполнение — отдельная ветка и отдельный этап, без бесконтрольного merge PR48 или сервера.

2. ОБЯЗАТЕЛЬНЫЙ ОХВАТ ОБОИХ ПРИЛОЖЕНИЙ
MASTER UPLOAD: исходное авторское аудио (один или несколько треков), картинки, модули, программы/метаданные каталога, дневниковые публикации и их media blocks/ContentLink, upload в существующий GAS/каталог. Часть операций метаданных без большого body тоже должны быть очередными и не теряться после lifecycle.
MASTER DOWNLOAD: каталог/установки доступных материалов, собственные опубликованные ресурсы при необходимости, восстановимые пакеты и другие управляемые приложением файловые выгрузки/обновления. Не приписывать приложению контроль над системной установкой APK; та выполняется Android/installer.
CLIENT DOWNLOAD: программы из каталога и все зависимости (модули, треки, фотографии/описания), выборочная установка и повторная установка, обновление ранее скачанных материалов при новой ревизии, будущие model/data assets если это относится к общему transport service. После успешной background install возможно офлайн воспроизводить все 3 трека; никакой дублирующей загрузки уже валидных зависимостей.
CLIENT UPLOAD: разрешённые экспорт/синхронизация/сохранение пользовательских материалов, записи дневника, аудио/фото/прикрепления, добровольно согласованные оценки/отзывы в будущем; модель не должна автоматически загружать локальный приватный материал на сервер. Только владелец/роль и явная операция или заранее согласованная синхронизация. Если какой-либо из перечисленных потоков ещё не существует, не изобретать новый сервис, но заложить поддержку в общем transfer API и покрыть тестами мок-transport.
ОСОБО: направления «скачивание» и «выгрузка» независимы по статусам и прогрессу; не смешивать очередь публикации и очередь выборочной установки каталога; пользователь видит их в одном понятном менеджере, где возможно фильтровать.
3. ЗАПУСК, ЛАЙФСАЙКЛ, ОС-ОГРАНИЧЕНИЯ
При явном запуске пользователем upload/download ОС принимает задачу продолжительного переноса и показывает системное уведомление. После Home/Recent Apps, открытия другого приложения, выключения экрана и обычного перезапуска Activity работа НЕ переходит в USER_PAUSED. Нельзя требовать, чтобы Flutter UI находился в памяти; file handles/URI permissions, auth, progress, job queue сохраняются на нативном/персистентном уровне.
Рассмотреть архитектурный выбор Android: API34+ JobScheduler user-initiated data transfer (UIDT) для явных длительных передач; foreground service dataSync с типом и уведомлением для поддерживаемых версий/случаев; WorkManager для отложенных/повторяемых небольших операций. Codex обязан зафиксировать выбор по minSdk/targetSdk/Android 14–16 и OEM-батарейным ограничениям, привести их, а не использовать «один WorkManager подходит всегда». Android 15 dataSync foreground service имеет суммарный лимит 6 часов/24 часа в фоне; Android16 WorkManager long-run может упираться в job quota; UIDT требует пользовательского действия и уведомления. Инженерная политика должна поддерживать graceful suspend/retry, а не гарантировать непрерывность при системном запрете. Официальные источники: https://developer.android.com/develop/background-work/background-tasks/uidt ; https://developer.android.com/develop/background-work/services/fgs/timeout ; https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running .
При force-stop пользователем, выключении телефона, переполнении диска, отзыве разрешений, logout и отсутствии сети задача честно WAITING/STOPPED и сохраняется для возобновления после разрешённого системного события/открытия приложения. Не обходить штатные политики Android и не требовать бесконтрольно «разрешить без ограничений батареи» как условие нормальной работы.
4. ПЕРСИСТЕНТНАЯ ОЧЕРЕДЬ И КОНТРАКТ ЗАДАЧИ
Перенести execution ownership из Flutter Activity в durable Android-capable job orchestration: data record с transferId, owner/role, direction, contentId/revision/manifest, dependency graph, local stable source URI, server uploadSessionId/jobId, expectedTotalBytes, uploadedAndAckedBytes, checksum, idempotencyKey, authState, createdAt/updatedAt, retryPolicy, errorCode, stage, lastReceipt; точные поля сверить с существующей №17 DB/queue, не дублировать source of truth.
Разделить состояния: QUEUED; RUNNING; VERIFYING; COMMITTING; WAITING_NETWORK; WAITING_POLICY; WAITING_AUTH; RETRY_SCHEDULED; PAUSE_REQUESTED; PAUSED_BY_USER (только явное действие!); COMPLETED; CANCELED; FAILED_RETRYABLE; FAILED_PERMANENT. Сворачивание приложения не должно являться user pause. Поддерживать безопасный owner-bound resume, on device reboot/app process kill/cold restart, восстановление после прерванной операции. Не обновлять UI фиктивными процентами при неизвестном объёме.
Последовательные chunks/HTTP attempts строго идемпотентны; сохранять подтверждённый сервером offset/chunk checksum и точный commit receipt. При сетевой ошибке сначала reconcile с сервером, не пересылать весь файл без необходимости; повторный commit не порождает дублей. При несогласованном partial сервере/коррумпированном upload — STOP с диагностикой, исходники сохранить. Локальные исходники защищены и не удаляются до подтверждения, cancellation не отменяет уже подтверждённую публикацию: для этого отдельное unpublish.
Для DOWNLOAD: staging → chunk/range resume при доступности на существующем сервере → validation expected length/hash/content manifest/revisions → atomic install/activation; отсутствие Range поддержки выявить честно и сообщить как P0 server compatibility issue. Неполный пакет нельзя выдавать как успешную установку. Повторные запросы не создают дубликаты треков/модулей или не обновляют revision задним числом.
Один owner работает, другой входит → старые приватные задачи не отправляются под другим аккаунтом. Refresh Google credentials через разрешённые auth flows, никаких фоновых silent logins в обход owner identity; если interactive login нужен — WAITING_AUTH и уведомление, очередь сохраняется. Manual logout не должен автоматически восстановить сеть от имени прежнего owner; после его явного входа resume возможен.
5. UX И ВИДИМОСТЬ СТАТУСОВ
Системное Android-уведомление пока идёт долговременная передача: имя задания/тип, реальные байты X/Y и процент только если Y известен, обновление без чрезмерных кадров, управление PAUSE/RESUME/CANCEL когда технически доступно; нажатие открывает нужную очередь. Пользователь может работать с приложением или блокировать экран. Само приложение при открытии мгновенно показывает реальные долговременные статусы из DB/OS, количество задач/ошибок/ожидающих, время последнего прогресса, назначение и суть задержки.
Привести кнопки: Пауза — только явное решение пользователя; Продолжить — явное ручное возобновление PAUSED_BY_USER или состояний, требующих auth; Ожидание сети/плановый ретрай должны возобновляться автоматически при разрешённых условиях. При коррумпированном контенте/нехватке места — понятная ошибка и действие пользователя. Событие background не менять бейдж «Передачи 4» на «Пауза пользователем».
6. СКОРОСТЬ И РЕСУРСЫ
Отдельно от background исправить/диагностировать слишком медленный transfer. Добавить безопасные технические показатели: HTTP latency per stage, chunk bytes, wall time, acked bytes throughput, chunk retries, compression/encryption overhead, storage/server verify time, bottleneck unknown tags. Не логировать токены, приватные тексты, аудио, URL с секретами. Предусмотреть умеренную пакетизацию/параллелизм только там, где сервер позволяет idempotent ordering; не перегружать GAS и не менять лимиты/ACL ради «ускорения». Согласовать realistic baseline на известной Wi‑Fi/сервер сети, измерять 1MB/15MB/50MB/несколько файлов; не утверждать фиксированную скорость без измерения.
Неизменность доставки при переходе UI и энергоэффективность важнее максимальной скорости в лаборатории. Метки времени/confirmed bytes должны позволять сравнивать сеть, сервер, хеширование и запись на носитель; исключить бесконечное ожидание при отсутствии прогресса. Bounded concurrency + exponential backoff + max retries + reconciliation/repair, не вечные hot loops.
7. ЗАЩИТА СУЩЕСТВУЮЩИХ ДАННЫХ И ГРАНИЦЫ
Основная рабочая ветка проекта и приватный main/GAS6/Google OAuth ACL/signing не менять без отдельного owner approval. Не переносить весь draft PR48 server со сторонними изменениями. При API несовместимости сформулировать точечный SERVER_CHANGE_REQUEST с byte-safe diff, snapshot/preflight, exact endpoints/ACL, тесты rollback/real receipts — сначала review, потом отдельное разрешение на production. Никаких вымышленно подтверждённых облачных публикаций.
Новый код должен мигрировать существующие USER_PAUSED/IN_PROGRESS задачи безопасно: не ставить задачу другого owner в работу, не терять отправленные байты, не стирать pending files, не делать массовый duplicate publish. Работать как APK update поверх MASTER27/CLIENT27 с сохранением Android package IDs, подписи, MediaStore/DB, истории, личных записей, настроек, каталоговых IDs. Конверсию очереди в новую схему покрыть отдельными native migration tests; выпуск и проверка двух APK должны быть согласованы как одна пара, но могут иметь независимый CI.
