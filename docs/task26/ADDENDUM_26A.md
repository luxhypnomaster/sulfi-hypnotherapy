Дополнение №26-А — Исследование биллинга ONREZA для MASTER
25.11.2026 | Действующее ТЗ №26 | Согласовано владельцем: включить практическое исследование
Цель: установить фактически доступный объём, последовательность и ограничения программного получения расходов и остатков ONREZA для MASTER → Управление → Состояние сервера. Не разрабатывать Android UI на этом этапе. Продолжать PR77 / feat/task26-onreza-staging, без повторения принятых локальных тестов без причины. Исходный ZIP v1.0 сохраняется; это дополнение расширяет его, не новый номер задания.
Порядок исследования
1. Read-only preflight: подтвердить доступность официального API/CLI, фактический workspace, тариф, scope токена. Изучить актуальную документацию https://docs.onreza.ru/ и help установленного CLI. Не предполагать наличие Usage endpoint по одному billing.read; не угадывать закрытые API и не обходить ограничения авторизации. Использовать уже разрешённый безопасный канал получения NRZ_TOKEN, не раскрывать значение.
2. Составить карту доступных показателей: тариф и расчётный период (границы/часовой пояс), включённый кредит, использованный кредит/начисления, остаток, прогноз отдельно от факта, подписка/счета, детализация Compute, PostgreSQL, Functions/BFU, KV, build, storage, traffic; квоты и единицы измерения. Для каждого — endpoint/CLI, параметры и порядок запросов, необходимый scope, источник, дата документации, фактический HTTP/CLI результат, схема очищенного ответа, единицы/валюта, время измерения и получения, точность и ограничения.
3. Практически выполнить только документированные read-only запросы после авторизации. Установить, какие запросы независимы, какие требуют workspace/project/period ID, поддерживают пагинацию/агрегацию, какова область (workspace/project/resource), лимиты и частота обновления. Сравнить до/после малой разрешённой нагрузки; если доступны только отложенные значения, указать наблюдаемую задержку или PENDING, не ждать бесконечно и не увеличивать нагрузку ради расхода. При возможности сверить с панелью владельца; не заявлять сверку без свидетельства. Отсутствие доступа, поля и документации различать.
4. Предложить контракт переносимого BillingAdapter: capability flags по каждому полю, source, scope, currency/unit, periodStart/End, measuredAt/fetchedAt, статус ACTUAL/ESTIMATE/STALE/UNAVAILABLE/PENDING, reason/error; money decimal или целые minor units. Не подменять фактические начисления тарифным расчётом; остаток, вычисленный из авторитетных сумм, маркировать derived, описать формулу и учёт корректировок. Указать периодичность и кэширование, ручное обновление, права server-side. Никаких административных ключей в MASTER/APK. Если read API отсутствует — явная недоступность и ссылка на панель; локальные счётчики отдельно как оценка.
Приёмка — дополнительно к T26-01…18
T26-19 — фактическая карта доступности показателей и источников, включая отрицательные результаты с причиной; отделить DOCUMENTED, VERIFIED_LIVE, BLOCKED_AUTH, NOT_DOCUMENTED, UNAVAILABLE, PENDING. T26-20 — воспроизводимый порядок официальных read-only запросов, очищенные примеры ответов, права, scope, единицы и ограничения. T26-21 — исследование актуальности/задержки и сверка с панелью при возможности; честная фиксация NOT_RUN/PENDING. T26-22 — проект BillingAdapter и матрица отображения MASTER по фактическим возможностям; без UI, без production integration. По каждому PASS/PARTIAL/BLOCKED, evidence отдельно.
Бюджет и границы
Исследование программного доступа к биллингу — самостоятельный результат, не блокировать остальные испытания только отсутствием Usage API. 10 ₽ — ориентир экономии, не подтверждённый автоматически контролируемый лимит; не считать его гарантированным. Финансовый gate: подтверждённый Hobby, отсутствие платных обязательств, минимальные ресурсы и ограниченная нагрузка, безопасное состояние после теста. Если тариф/условия оплаты или разрешение на создание ресурсов не подтверждены, STOP для provisioning, read-only продолжить. Не переходить на платный тариф, не подключать карту, не менять подписку/ACL. GAS6/main/Android/production/№25 не трогать. Не раскрывать секреты и закрытые идентификаторы в shared отчётах.
