# Цель, объём и порядок исполнения
Создать один устойчивый проект protocol22-staging с Compute (предлагаемое имя protocol22-api), управляемой PostgreSQL, Functions и KV. Не одноразовая демка: сохранить идентификаторы и конфигурацию, последующие ТЗ расширяют тот же проект. Проверить возможность лёгкой проверки сессии и HEAD без пробуждения Compute/SQL. Синтетические данные исключительно. Реальный Google OAuth, Auth19 интеграция, миграция SQLite, полный P22, Drive gateway, production, реальные данные, расписание и Android не входят в этап. GAS6 — действующий baseline, без переключения. Не заявлять готовность продукта.

## A. Предполётный контроль (обязателен)
- Репозиторий luxhypnomaster/sulfi-hypnotherapy; публичность подтверждена 25.11, main default. Изучить реальный Git baseline, серверные файлы, PR №22–25 и их зависимости; не считать draft merged. Выбрать точный SHA, минимальный build context, отделённую ветку feat/task26-onreza-staging (при наличии своей ветки переиспользовать). Не менять main, Android, CI релизов, signing, GAS6, OAuth/ACL действующих систем. Не создавать второй конкурирующий backend. Если существующий Node/SQLite пригоден — переиспользовать runtime/config/build; если нет — минимальный bootstrap в том же серверном контуре, с планом подключения существующего API. Зафиксировать причину, не переносить тестовую схему в финальный домен без ревизии.
- Прочитать профиль ONREZA §11 и IAM/SNAP/HEAD; CORE независим от провайдера. Уточнить реальные CLI/API и документацию ONREZA; не выдумывать URL/команды/SDK. Сначала проверить безопасный доступ по 05_ACCESS.md: identity, workspace ID, Hobby, кредит, inventory, ставки Compute/SQL/BFU/KV/хранение/трафик, режимы сна и исчерпания; учитывать лимиты существующих ресурсов. Сверить workspace Alchemic project, не предполагать соответствие по имени аккаунта. Если неоднозначно — STOP live. Никаких платежей/платного тарифа/карты/обязательств. Целевой расчётный максимум добавочного расхода 10 ₽ включённого кредита; если лимит не подтверждён владельцем или невозможно доказать ограничение — STOP до подтверждения. Расчёт всего окна теста и остаточного расхода после него, включая SQL/Functions. Не поддерживать искусственный keep-alive. Не создавать ресурс при неопределённом тарифе/цене/границе расходов. При неподтверждённом сне безопасно остановить созданные Compute и SQL (не удалять) если поддерживается, иначе запросить решение до создания. Не расходовать кредит нагрузочными тестами.

## B. Постоянный STAGING и минимальный код
Inventory → найти или создать ровно один целевой проект, Compute, Postgres, Functions и изолированный KV namespace. Если платформа устроена иначе — зафиксировать фактическую модель; никакого дублирования/удаления. Повторный запуск обновляет ресурсы по сохранённым IDs. Если единственный лимит PostgreSQL занят — STOP, ничего не удалять. Не импортировать весь Android repo, не включать auto-deploy main. Официальный deploy из конкретного серверного commit/build context, воспроизводимый manifest, lockfile, runtime, PORT/bind, start command, лимиты, секреты по именам, deployment revision, rollback. /healthz: минимальный status/environment=staging, 404/405; не раскрывать служебные детали. Секреты/privileged IDs/логи не в публичном Git.

## C. Auth-first, затем HEAD
PostgreSQL — единственная авторитетная БД идентичностей, установок, сессий, grants, HEAD. Изолированные миграции/fixtures для синтетических аккаунтов, версий прав, тестового immutable snapshot и durable projection queue. KV — ограниченная восстанавливаемая проекция; никаких Google refresh tokens, паролей, реальных профилей или личной терапии. Защищённый тестовый вход/публикация: не предоставлять публичную произвольную регистрацию. Синтетические signing credentials в защищённом runtime, не в репозитории. Проверить подпись, срок, issuer/audience, scope, session/roleVersion, fail-closed. Отсутствие KV-записи не означает новый аккаунт: после подтверждения идентичности искать SQL по issuer/subject; восстановить существующий либо идемпотентно создать новый с устойчивым User ID, привязать установку. Произвольный client ID не удостоверение личности. Явно невалидный запрос не пробуждает SQL. Не создавать вторую Android auth; действующий Auth19/coordinator и OWNER/ADMIN/grants остаются основой следующего этапа.
Критические действия, отзыв/назначение ролей, backup/restore, закрытые материалы требуют актуальной авторитетной проверки. Stale KV/JWT, forged headers, прямой Compute URL, failure=open не дают обхода. TTL, допустимое окно устаревания отдельно документировать, не обещать немедленную консистентность KV. Ограничение частоты не заменяет ACL.

## D. Общий ProjectionPublisher и HEAD
SQL commit + долговечная запись о доставке (transactional outbox или эквивалент с доказанными гарантиями) → versioned KV projection. Retry, idempotency, invalidation, rebuild, контроль порядка/регрессии, сбой между commit/write. Не предполагать CAS и прямой Compute KV SDK; изучить защищённый вызов Function из worker либо SQL binding, если реально доступны. waitUntil не durable очередь. Если невозможно доказать корректность порядка, STOP/PARTIAL, не публиковать небезопасную схему. Без постоянно активного repair. Изолированный тестовый namespace; нельзя чистить весь workspace.
HEAD в KV только после проверки immutable snapshot и зависимостей и авторитетной публикации. Существующий S-X-CAT-HEAD-001 неизменен: scope, catalogRevision, snapshotId, snapshotHash, schemaVersion, createdAt и независимые ratingsRevision/hash. Не добавлять обязательные wire fields; не путать диагностические маршруты с P22. Нет утечки private scope, нет неподтверждённого HEAD, нет регрессии. Сбой: последний корректный HEAD только при допустимой политике доступа, иначе явная недоступность и CLIENT lastGood. Идентичная пересборка не меняет revision/hash. Штатное чтение из KV без SQL/Compute; miss — контролируемый fallback.

## E. Переносимость и проверка
KVStorageAdapter get/put/delete/TTL + capability contract, FunctionRuntimeAdapter request/context/secrets/response, ProjectionPublisher, SQL repository. CORE без ctx.kv/ctx.sql/ONREZA DSL; platform binding отдельно. In-memory fake и контрактные тесты TTL/miss/задержки/отсутствия CAS, отказов и изоляции. Redis/Valkey/SQL fallback — варианты, не реализовывать лишнее. Проверить фактический pipeline before-cache/fail-closed при поддержке; безопасность важнее экономии.
Провести малые тесты HTTPS, повторного deploy, rollback readiness, cold/warm latency, Function-only с подтверждённым сном Compute и SQL (наблюдение состояния, не только задержка). Не опрашивать постоянно. Usage до/после с timestamps, реальная стоимость/задержка показаний, PENDING если reconciliation не завершён. Отдельно проверить сетевой маршрут Codex; дать HTTPS URL для владельца, российская/зарубежная физическая приёмка отдельно. Не больше двух одинаковых сбоев без новой гипотезы. Все проверки по 02_ACCEPTANCE.md. Оставить проект/ресурсы и код в согласованном экономичном состоянии; не удалять. При блокере сохранить локальные результаты и инструкцию возобновления с той же ветки/IDs.
