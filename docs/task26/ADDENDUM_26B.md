Дополнение №26-Б — Версионный KV и автономность Functions ONREZA
26.11.2026 · v1.0 · согласованный узкий эксперимент в рамках №26
Цель: установить, пригоден ли фактический native KV существующего STAGING для выбора максимальной доступной корректной версии публичного HEAD, безопасной очистки старых ключей и чтения через Function без пробуждения Compute/SQL. Не реализовывать полный publisher, P22 IAM или клиент. Остаток недельной квоты владельца до запуска: 3%; это наблюдение, не программно контролируемый бюджет и не требование исчерпать квоту. Не выполнять работу ради расхода.

2. Порядок и контрольные точки
B0 — read-only. Зафиксировать exact code/active release, plan, runtime bindings, документированные signatures/capabilities, доступный non-waking control-plane источник наблюдения Compute/SQL и известные лимиты. Если list отсутствует у фактического native binding, зафиксировать BLOCKED_CAPABILITY, не заменять его list другой технологии, не начинать опасную уборку; независимое no-wake испытание с фиксированным known key допустимо и не доказывает version selection. Если нет достоверного state readback, заранее пометить no-wake UNVERIFIABLE, а не тратить квоту на поиск закрытых API. Сохранить checkpoint.
B1 — минимальная диагностика. Переиспользовать существующий protected probe, fixed operation с валидированным runId и серверно заданными ключами/значениями, никаких произвольных KV команд/ключей/SQL. Отдельный prefix synthetic26:task26:version-probe:<runId>: и независимый синтетический scope; только фиксированные ключи текущего запуска, список с ограничением и точной фильтрацией. Записать в локальный санитизированный журнал ожидаемые имена ключей ДО записи. Объекты малые, до 512 B каждый, максимум 5 ключей одновременно и 30 штатных native HTTP запросов за этап, включая проверки закрытия; без массовой нагрузки. Не больше одного необходимого code deploy через уже подтверждённый Git build (без повторного rollback-теста); выключение окна тем же штатным способом, не считать его дополнительной исследовательской сборкой. Если необходим больший объём, STOP с предложением. Сохранить предыдущий рабочий release pin. До binding проверять STAGING, отдельную случайную capability (не NRZ_TOKEN), hash, независимый expiry ≤1200s, fixed method/path/body, deny by default; без секретов/URL/IDs в shared evidence. Проверить отказ без capability и неверной операции, test closure; не открывать действующие HEAD/publisher.
B2 — версии и очистка. На документированных native primitives: создать V1 и V2 отдельными неизменяемыми ключами с численно упорядочиваемой ревизией и проверяемой целостностью/синтетическим expected scope (hash не доказательство авторства; не принимать реальные grants). Выбрать max валидный доступный объект по числовой ревизии, а не по порядку выдачи или времени. По возможности принудительно проверить малый page size и cursor (не умножать запросы без необходимости), отфильтровать соседний synthetic scope; неполная/ошибочная пагинация означает no cleanup. Удалить V1 только когда V2 проверен; записать V3 отдельным ключом, сохранить V2. Поздно восстановить тот же V1 с идентичными bytes — максимум остаётся V3; следующий моделируемый pre-publication sweep адресно удаляет только известный старый V1; V2 можно удалить только при подготовке следующей публикации по REQ-ONR-033 при подтверждённом V3, но дополнительную V4 ради этого не создавать. Не удалять lastGood при неопределённости. Проверить отсутствующий/испорченный объект и несоответствие scope/hash; не возвращать невалидный HEAD, не уничтожать последнюю корректную версию. Локальный адресный тест high-water: увидев V3, клиентская модель отвергает V1/V2 и одинаковую ревизию с другим hash. Это не тест Android. Не требовать глобальной согласованности по одному региону. Сначала использовать ограниченный TTL для основных синтетических опытов, достаточный для B2/B3 с учётом idle; если документированный set без TTL и адресная очистка подтверждены, допускается одна отдельная no-TTL запись с заранее сохранённым точным ключом и проверенным recovery после аварии. Иначе no-TTL остаётся OPEN. Не переносить TTL синтетической диагностики на требования реального HEAD. Не проводить quota exhaustion или multi-region нагрузку.
B3 — no-wake. Отдельно от write/setup, дождаться штатного idle по существующей конфигурации, проверить provider observed state Compute (все обслуживающие экземпляры) и SQL штатным non-waking control plane. Не будить сервис health/SQL query ради наблюдения. Выполнить один малый Function-only native read синтетического max valid HEAD (либо фиксированного key, если list blocked), затем один повтор только если нужен для различения результата. Зафиксировать active deployment, route Function, UTC время, provider state/events до/во время/после, доступный BFU/CU/Usage до/после и latency. PASS no-wake только если наблюдение охватывает интервал запросов и исключает короткое пробуждение обоих компонентов; before/after stopped без непрерывного доказательства — PARTIAL, latency/config idle/отсутствие SQL в коде не доказательство. Снимки панели/Usage с freshness, округлением и задержкой сверки; если не доступны без владельца, PENDING, запросить только следующий необходимый замер, не ждать reconciliation. Не экстраполировать на месяц/пользователей.
B4 — обязательное завершение. После каждого checkpoint сохранять журнал ключей и результат; не удалять V2/V3 между B2 и B3, если они нужны для следующего чтения. При завершении эксперимента и в finally, включая исключения/прерывание где среда позволяет: адресно удалить исключительно известные ключи текущего run по журналу, verify miss, scope isolation; при недоступной очистке перечислить остатки и безопасный recovery по runId, не чистить весь namespace/workspace. Закрыть diagnostic mode; проверить 403 со старой capability, без health-запроса ради сна. Если rollback требуется по ошибке, проверить observed active generation и независимый expiry (rollback может восстановить старое окно), закрыть снова. Вернуть SQL/Compute в согласованное экономичное состояние, без удаления ресурсов. Если прерывание внезапное и finally не выполнен, на следующем запуске обязательный read-only resume/cleanup до новых экспериментов. TTL временных ключей — резерв при поддержке, не substitute cleanup. Новых возможностей P22 не включать.
3. Приёмка (добавляется к T26-01…22, не закрывает их автоматически)
T26-23 — native capability: официальный API и live list/get/delete, scoped prefix/cursor, документированная возможность no-TTL отдельно; свидетельства реального binding, границы региональности и ошибок. PASS только для реально проверенных возможностей, иначе PARTIAL/BLOCKED; никаких выводов о global CAS.
T26-24 — versioned selection и bounded cleanup: V1/V2/V3, поздняя V1, числовой max валидного, сохранение последнего корректного, неполный list/невалидный объект и scope отказ, high-water модель. Отдельно LIVE и CONTROLLED; не выдавать controlled failure injection за реальный provider lag. Документировать, что latest visible не равен гарантированно свежему SQL HEAD.
T26-25 — Function-only read и no-wake: отдельно native max/known key result, latency, observed Compute и SQL, evidence coverage, фактические Usage или PENDING. PASS no-wake только при достаточной телеметрии; без неё PARTIAL. Не объявлять live IAM, auth/session/outbox/SQL migration, реальный HEAD, клиентскую синхронизацию или full P22 E2E пройденными.
T26-26 — безопасность/финал: exact target, минимальный diff, scoped keys, bounded operations, отказ без auth/неверная операция, отсутствие утечек, cleanup verified, modeoff403, состояние ресурсов, no paid commitments, сохранён предыдущий release. Если cleanup/closure не подтверждены — BLOCKED/PARTIAL, сообщить сразу; не выдавать общий PASS.
4. Экономия, STOP и отчётность
Адресные тесты fixed probe, selection и security/cleanup, связанный regression gate при изменении маршрута/guard; не запускать Flutter/APK, полную матрицу 69 Node тестов только ради расхода (при реальном P0 изменении выполнить необходимый security regression gate). Не повторять одинаковый сбой более двух раз без новой гипотезы. Не повторять создание ресурсов, OAuth, TCP, SourceV2 QUIC, rollback/SELECT1/set-overwrite, сборку и исследование биллинга. Не расширять на GDRIVE-01, live IAM/SQL, full publisher, реальный каталог или Android. STOP при неверном target/платных обязательствах, неограниченной стоимости, отсутствии safe access/cleanup, конфликте Git, невозможности защитить probe, исчерпании среды; не обходить ограничения. Приоритет B0→B1→B2→B3, B4 неотложен при любом исходе.

Не присваивать PASS прежним пунктам без нового свидетельства. Ответить: подтверждён ли native list; возможен ли versioned HEAD без CAS; безопасна ли очистка; доказан ли no-wake; какой минимальный следующий шаг для №27. 5. Предвыпускная ревизия и совместимость
Ревизия 26.11.2026: сверены PR77 head, пять адресных файлов, исходное ТЗ, №26-А, REQ-ONR-032…035, последний RESULT/RUNTIME/KV_ORDERING/ISSUES и регламент экономии. Исправлено: (1) не считать list поддержанным до проверки native binding; (2) не снимать старые guards и не смешивать fake/реальный provider; (3) отделить максимальную видимую ревизию от SQL freshness и security; (4) запрет cleanup при неполной выдаче, адресный cleanup с журналом; (5) before/after stopped недостаточно для полного no-wake; (6) финансовые данные PENDING не блокируют безопасную малую проверку, 10 ₽ не гарантированный cap; (7) rollback/expiry и финальная проверка закрытия обязательны; (8) ограничить запросы/сборки, исключить GDRIVE-01, реальные IAM/SQL и повтор пройденных тестов.
