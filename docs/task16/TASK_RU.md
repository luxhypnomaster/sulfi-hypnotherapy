# Техническое задание №16 — «Сервер Проекта Алхимик»

## 1. Результат, который надо получить

**Живую, полнофункциональную, доступную владельцу с телефона экосистему**: приложение Сульфи (мастер) ↔ Google Apps Script **«Сервер Проекта Алхимик»** ↔ Google Drive ↔ клиентская редакция Сульфи. Не ограничиваться только дневником, только текстом, только маленькими вложениями, localhost, emulator или FakeProvider. Сервер и приложения должны уметь создавать/хранить/публиковать/читать/выгружать/скачивать/переустанавливать реальные материалы всех согласованных типов. Два APK на одном рабочем backend, одна Flutter codebase, локальные данные сохраняются.

### Сквозные пользовательские сценарии, обязательные в целевом контракте

**S1.** Автор создаёт/редактирует дневниковую запись с категориями, текстовыми блоками, фотографиями, аудио, видео, порядком блоков и вложенными ссылками на материалы; черновик может быть офлайн. Публикует выбранную версию на сервер; с клиентского APK скачивается и корректно отображается. Правка заголовка не загружает всё медиа заново; изменение одного файла не перезаливает остальные. Без согласия автора не публикуется личное.

**S2.** Клиент получает каталог доступных записей, обложки, вложения и поток обновлений; умеет выбирать и загружать материалы, читать/слушать/смотреть, отмечать прочитанное локально, сохранять офлайн, восстанавливать передачу, различать новую редакцию и переобъявление, корректно видеть архив/закрытие/срок годности. Автор управляет публикацией, клиент не может писать за автора.

**S3.** Автор выгружает на Google Drive версии ZIP-пакетов сеансов, шаблонов, модулей и музыкальных/аудионаборов, метаданные и манифест, проверяет SHA-256 и целостность. Клиент получает разрешённый каталог, выбирает пакет, скачивает из Drive **через серверный процесс доступа** (не из локальной заглушки), проверяет manifest/digest, импортирует в текущую библиотеку без порчи существующих файлов; можно скачать повторно, обнаружить новую версию, не дублировать идентичный пакет.

**S4.** Автор добавляет/обновляет аудио и видео большой длительности и обычные изображения; сервер управляет resumable/chunk transfer, прогрессом, паузой/возобновлением и проверкой данных, обеспечивает безопасную доставку/проигрывание в клиенте. Ограничения платформы Google должны обрабатываться с явной диагностикой, без silent success и скрытого обрезания файлов.

**S5.** Автор и клиент авторизуются там, где требуется приватный доступ, с проверяемыми сервером субъектами и ролями; публичное читается только после явной публикации. У автора отдельно черновики/личные записи, у клиентов нет права редактировать чужие записи, видеть секреты или управление сервером. Клиентская сборка и переключатель роли в UI не являются доказательством полномочий.

**S6.** Работа без сети: локальный просмотр скачанного, очередь публикаций/загрузок, retry/idempotency, точные конфликты/диффы, фоновое возобновление по возможностям Android, контроль свободного места, безопасный прогресс. Ошибки показываются, не выдают локальное действие за облачное.

**S7.** Старая авторская APK `ru.sulfi.sulfi_hypnotherapy` обновляется поверх без сброса пользовательских данных/смены подписи, клиентская APK остаётся отдельной `ru.sulfi.sulfi_hypnotherapy.clienttest` (позже можно переименовать на отдельной миграции). Две сборки с настоящим серверным endpoint из одного CI SHA.

**S8 — НОВЫЙ ОБЯЗАТЕЛЬНЫЙ КАТАЛОГ ПУБЛИКАЦИЙ.** Автор в уже существующей Библиотеке выбирает трек, модуль, шаблон или сборку, оформляет **карточку с названием, аннотацией, описанием, категориями, тегами, языком, обложкой, автором/правами, видимостью и версией**, проверяет состав и зависимости, выгружает изменённые байты в Drive и только после byte/hash readback явно публикует. В master UI есть раздел управления карточками (черновики/опубликовано/архив, изменение аннотаций и версий, снятие с публикации, повтор upload). Клиент видит метаданные и кнопки **Скачать/Установить/Обновить**, получает ровно необходимое аудио для выбранного модуля/шаблона через `LocalCatalog`, сохраняет собственные изменённые копии. Предпрослушивание до скачивания не навязывать: K-016 ранее его исключал. Подробный UX, state machine и API — `CONTENT_CATALOG_AND_STORAGE.md`.

**S9 — ФИЗИЧЕСКИЙ DRIVE ROOT И МИГРАЦИИ.** Под существующей приватной папкой `Проект Алхимик` создать единожды отдельную `Хранилище Сервера Проекта Алхимик` с подпапками **Система, Дневник (включая изображения/аудио/видео), Библиотека (библиотечные аудиотреки, модули, шаблоны, сессии, сборки), Медиа, Пакеты, Каталог, Техническое**. Автоматический `bootstrap` по IDs/parent, без дублирующих папок и без публикации чужих частных файлов. Проверять актуальный ACL исходной папки, иначе остановить небезопасную запись. Физическое хранение отделено от каталога.

**S10 — НЕЗАВИСИМЫЙ PREFLIGHT ДО КОДИНГА.** Прежде больших изменений проанализировать source №15, прежние K/F решения, живые Google/Flutter/GitHub ограничения и этот пакет, записать `PREFLIGHT.md`: consistency, auth blockers, реально поддержанные GAS request/response, media transport, Drive ACL, custom copies, migrations, C0 acceptance. Исправить обнаруженные несоответствия до построения API; отсутствие OAuth не отменяет разработку, но запрещает объявлять LIVE.


## 2. Порядок реализации без лишних задач

**A. Реальная база + preflight.** Прочитать отчёты №15 и SERVER_HANDOFF/API_CONTRACT.yaml, изучить текущие Flutter providers, AudioAsset, Library, Diary, ZIP, Module/Template/Session/ContentLink. Проверить HEAD, PR, ветку и неизменность данных. Не писать вторую несовместимую подсистему параллельно.

**B. Полный серверный код и индексируемое хранилище.** Написать рабочий Apps Script V8 backend с `doGet/doPost`, управлением Google Drive, auth grants, хранилищем пользователей/объектов/ревизий/медиа/пакетов, catalog/feed, import/export, publish, resumable upload/download, журналом ошибок, конфликтами, возвратом стабильных ошибок. Код должен реально компилироваться GAS и проходить Node test harness. Настоящая схема в SERVER_REQUIREMENTS.md, MEDIA_AND_PACKAGES.md, SECURITY_AND_IDENTITY.md, DATA_AND_REVISIONS.md и обязательно `CONTENT_CATALOG_AND_STORAGE.md`.

**C1. GitHub CI/CD.** Путь доставки выбран владельцем: **Codex → GitHub Actions → `@google/clasp` → Google Apps Script**. В этом же №16 создать защищённые workflows для независимых Node/Flutter тестов и для ручного production-развёртывания из GitHub с `AUTH_PENDING` сценарием (`GITHUB_ACTIONS_DEPLOYMENT.md`). OAuth Codex не требуется. Владелец прошёл Google consent в Cloud Shell, но завершение `clasp login` и наличие GitHub Secret НЕ подтверждены. Workflow сначала создаётся и тестируется без секретов.

**C2. Настоящий Google проект.** После получения безопасного завершённого OAuth в GitHub Secret и проверки `script.projects`/`script.deployments` создавать через GitHub Actions проект **«Сервер Проекта Алхимик»** (один, private), загрузить ВЕСЬ код и manifest, readback, задать нужные защищённые свойства и папки Google Drive, создать версию и настоящее web app deployment. Проверить авторизацию и негативные обращения. **Не создавать отдельный staging/PoC.** Доступность одноимённого старого проекта не использовать и не угадывать его состояние.

**D. Автор/клиент.** Реализовать авторский каталог карточек/аннотаций для треков, модулей, шаблонов, сборок, публикационный workflow с dependency-check и client каталог с выборочной установкой; затем подключить реальный transport, OAuth там где необходимо, offline queues, библиотеки, дневники, пакеты и media transfer. Сохранить старые данные и UI, не менять несогласованный дизайн без необходимости. Обеспечить полные маршруты для видео и аудио как отдельных типов, а не ссылки с невыполнимой заглушкой.

**E. Исправить опасные зависимости.** №15 G3 exact old/new audio bytes + immutable revisions/refcount/rollback, не удалять старое; использовать расширяемый контракт. Если миграция не доказана безопасной, отключить только опасную запись с чётким статусом, но остальные полноценные публикации и скачивания реализовать. Не терять пользовательские данные ради сдачи требований.

**F. Проверка и поставка.** Node/Flutter/contract/fault/security tests, затем LIVE контрольную публикацию и загрузку (только с правомерно созданными контентом/ACL), две APK в GitHub CI. Синтетические данные допустимы только как внутренние контрольные образцы и не должны быть отдельным публичным тестовым сервером. Реальное облако нужно отдельно пометить LIVE/NOT LIVE. Owner phone QA — только после его фактических испытаний, не автоматический PASS.

## 3. Условия реальной готовности

Для `SERVER_LIVE` нужны: точный Drive data root (не For_Codex), idempotent folder bootstrap и проверенные ACL, не менее одного реально опубликованного аудиотрека с аннотацией и одного модуля с зависимостями, выборочная установка на клиенте; настоящее имя проекта, scriptId, инвентаризация HEAD и загруженного manifest, версионированный deployment, фактически отвечающий `/exec`, реальные защищённые Drive folders, подтверждённый auth deny, запись/чтение/скачивание аудио+видео+ZIP и реальное приложение клиента. Для `FULL_E2E` — соответствующие запросы от авторского и клиентского транспорта к этому deployment и реальные байты, не эмулятор. За все неподтверждённые части дать `BLOCKED` или `NOT_RUN`, без рассказов об «успехе почти готового сервера».

## 4. Неустранимые условия безопасности (не «усечённость»)

Не выкладывать секреты/refresh token в APK, Git, отчёты или чат. Не делать `anyone: writer` на проект, публикации, личные медиа или корневую папку. Не превращать публичную читательскую ссылку в разрешение публиковать/удалять. Не пытаться обойти OAuth consent. Исключить перезапись/удаление чужих файлов без проверки владельца, ACL, etag и revision. Сохранять обратную совместимость и бэкапы. Если облачный runtime не имеет прав управлять Apps Script — это реальная граница доступа, НЕ повод подделать deploy и НЕ причина прекращать программирование.

## 5. Оговорка о реальных лимитах

Не ставить искусственную цифру размера «ради сдачи теста». Реализовать chunked/resumable transfer и динамическое поведение. Apps Script исполняет функцию не более 6 минут, `UrlFetchApp` ограничен размером запросов/ответов; Drive API поддерживает resumable uploads. Для больших приватных видео нужно подтвердить рабочую схему выдачи без распространения owner credentials; варианты — Google OAuth + ACL на конкретные файлы или проверяемый chunk relay через GAS. Контракт не должен называть это потоковым CDN, если это последовательная загрузка. Полную безграничную раздачу видео GAS не гарантирует.

## 6. Включённое в UI владельца разрешение API

На скриншоте 10.11.2026 видно «API скрипта приложений Google Apps — Включено». Это **разрешение доступа сторонним приложениям** к управлению Apps Script, а не OAuth grant Codex. Требования доступны в DEPLOYMENT_AND_PERMISSIONS.md. Сначала пробовать официальные подключённые механизмы, не гонять бессмысленные повторные 401. Владелец не должен заходить на ПК/в редактор. Если нужного grant нет — честный конкретный blocker, допускается только простой consent link, предоставленный авторизующим реальным приложением, без пересылки приватных кодов через чат.

## 7. Отчётные артефакты

В `For_Codex/Отчёты — Задание 16` дать `PREFLIGHT.md`, `CATALOG_TESTS.md`, `DRIVE_TREE_AND_ACL.md` (без private file IDs в публичной части), полный Git commit/PR, действительный scriptId/deployment `/exec`, endpoint/environment information, data root IDs в защищённой отчётности без секретов, source+hash readback, таблицу операций, доказательства реальных upload/download media ZIP, обе APK, тесты, список неработающего. Если cloud недоступен — отделить `FULL_CODE_IMPLEMENTED` от `CLOUD_WRITE_BLOCKED`. Чёткая команда resume, не повторять уже готовые шаги.

## ОБЯЗАТЕЛЬНЫЙ КОНТУР КАТАЛОГА И ПАПОК — не откладывать после сервера

После проверки существующей структуры Git реализовать **полный путь авторская библиотека → экран подготовки публикации/аннотация → upload immutable bytes → manifest → online catalog → клиентский поиск/карточка → выборочная установка**. Требования, типы, статусы, методы, UI, ACL, миграции, критерии — **CONTENT_CATALOG_AND_STORAGE.md**. Новое требование обязательно в текущем №16, не откладывать на следующий номер и не подменять одной кнопкой «Экспорт ZIP». У каждого трека и модуля автор может задать shortAnnotation и метаданные; состав модуля фиксируется точными версиями треков. Клиент скачивает и устанавливает недостающие треки из каталога, с проверкой SHA и сохранением собственных модификаций. Дневники и публичные материалы не смешивать по доступу.

Сервер должен при первом успешном owner-admin bootstrap **создать и повторно использовать** дерево `Проект Алхимик/Хранилище Сервера Проекта Алхимик/` с системной, дневниковой, библиотечной, медиа, пакетной, каталоговой и технической зонами (полный список в новом документе). Bootstrap идемпотентный, с ACL/readback, собственными folder IDs; нельзя плодить дерево при каждом deploy. Если права родителя несовместимы с личными данными, fail-closed с безопасным отдельным private root. Работа только с телефона, GitHub Actions + clasp; наличие CI без OAuth не означает реального создания Drive-папок.
