# №16 — автоматическая публикация «Сервер Проекта Алхимик» из GitHub Actions

## Историческое уточнение владельца, 10.11.2026

Прошлый прямой путь «Codex → Apps Script API» давал `CREDENTIALS_MISSING`/HTTP 401 в среде Codex. Пользователь нашёл официальную цепочку **Codex изменяет GitHub → GitHub Actions → `@google/clasp` → Google Apps Script** и начал на телефоне `clasp login --no-localhost` в Google Cloud Shell. На скриншоте пользователь дошёл до запроса OAuth, подтвердил все scopes, браузер выдал `localhost:8888?...code=...`; но адрес **НЕ был введён обратно в Cloud Shell** и нет подтверждения `clasp show-authorized-user`. Таким образом **согласие Google показано, токен `~/.clasprc.json` и готовая авторизация clasp пока НЕ подтверждены**. Не повторять ввод OAuth-кода через чат; пользователь не хочет задерживаться на этом этапе. Не требовать PC, физическую клавиатуру, Apps Script editor или чтение/пересылку токена в чат. Не предполагать, что GitHub уже имеет секреты.

Официальная документация: https://developers.google.com/apps-script/guides/clasp (раздел `CI/CD for Apps Script with clasp and GitHub Actions`), https://github.com/google/clasp . В GitHub Actions OAuth нельзя получить интерактивным браузером. Для реального деплоя требуется безопасное заранее выданное разрешение; **никакая сборка YAML не создаёт его сама по себе**.

## Обязательные результаты в этом же №16

**НОВЫЙ ОБЯЗАТЕЛЬНЫЙ ОБЪЁМ:** `CONTENT_CATALOG_AND_STORAGE.md` является частью server source и двух Flutter APK: master публикационный редактор/аннотации, реальный клиентский каталог/выборочная установка, идемпотентный private Drive root `Хранилище Сервера Проекта Алхимик` внутри владельческого проекта с ACL check, отдельные папки библиотеки/дневника/медиа/пакетов/каталога. GitHub Action после OAuth не должен создавать пустой Script и делать `LIVE` до успешного `storage.bootstrap` readback и catalog smoke tests. Предварительная проверка по `PREFLIGHT_AUDIT.md`.


1. В существующий GitHub репозиторий `luxhypnomaster/sulfi-hypnotherapy` (проверить фактический origin) добавить **отдельный тестовый GitHub Actions workflow** для GAS source: Node tests / lint / contract / security, проверка скомпилированного исходника и manifest, без OAuth и без реального cloud deploy. Изменения PR/посторонних веток не должны получать продакшн-секреты.
2. Добавить **отдельный защищённый workflow `.github/workflows/alchemist-server-deploy.yml`** (или равноценный существующий) с `workflow_dispatch` на защищённой ветке/окружении `alchemist-production` и ограниченными `permissions`, `concurrency`; только после прохождения тестов и разрешения владельца — создание/обновление production GAS. Не делать автодеплой при каждом push в необъединённую feature-ветку; CODEX не должен писать секреты в YAML или в CI log.
3. Использовать текущую совместимую версию `@google/clasp` и **реально проверенные команды установленной версии**: `clasp create-script --title 'Сервер Проекта Алхимик' --type standalone`, `clasp push`, `clasp create-deployment` / `update-deployment`, `clasp list-deployments`, `clasp pull`, `clasp show-authorized-user`. Проверить доступный синтаксис, поскольку CLI v2/v3 отличаются. `push` полностью заменяет удалённые source-файлы — deploy только из полного собранного source и после CI checks.
4. Предусмотреть GitHub Actions Secret **`CLASPRC_JSON`** с содержимым **готового, после полностью завершённого `clasp login`,** локального `~/.clasprc.json`. Это *секрет с refresh token*, никогда не коммитить и не писать в логи, APK, Google Docs, отчёты. `CLASP_JSON`/`scriptId` использовать только после фактического создания/верификации проекта; отложить захват и хранение ID до доступных credential. Параметры конфигурации можно вынести в GitHub Environment, никогда не передавать их через user-visible chat. Секреты должен вводить только владелец в защищённый GitHub UI с телефона либо иной доверенный авторизованный секретный канал; Codex не вправе извлекать их из Google Drive/ChatGPT коннекторов. Никаких setup-просьб прямо сейчас, если пользователь не хочет возвращаться к OAuth.
5. В workflow реализовать **`AUTH_PENDING` → `CREATE_ONCE` → `SOURCE_PUSHED` → `DEPLOYED` → `LIVE_VERIFIED`**. При отсутствии `CLASPRC_JSON` — понятный отказ `GITHUB_SECRET_MISSING`, **не создавать новый проект и не объявлять live**. При `clasp create` сохранить непубличный `scriptId` и обеспечить идемпотентность/надёжную фиксацию соответствия проекту (readback из Google, защищённая конфигурация/артефакт); **после неудачной попытки не создавать второй проект с тем же именем вслепую**. Не удалять старый Script `Сульфи — дневник`.
6. После успешной авторизации GitHub: 1) create-once один PRIVATE Apps Script «Сервер Проекта Алхимик», 2) полный push GAS+manifest, 3) readback source+version, 4) versioned deployment с правильными web app/executeAs/access настройками, 5) **проверка parent ACL, создание одного data root и всего folder registry с readback**, 6) безопасные health и negative auth tests, 7) **реальная каталогизация одного аннотированного трека и модуля с зависимостями, проверка публикации/клиентского selective install**, плюс синтетические media E2E (PNG/audio/video/ZIP), 8) записать доказательства в «Отчёты — Задание 16»; 9) две Flutter APK. Если GitHub Secret отсутствует, весь backend, tests, workflow и Flutter transport всё равно завершать.
7. Защитить CI: `secrets` НЕ доступны PR из форков или произвольному pull_request/коду; permission минимум `contents:read` в обычном CI, право записи только для отдельной задачи безопасной фиксации project metadata если действительно необходимо; environment approval и manual dispatch в production; `concurrency` не допускает конкурентных деплоев; pinned actions versions/commit SHA при необходимости. Не использовать `pull_request_target` для небезопасного кода. Секретный файл создавать с `umask 077` из `secrets.CLASPRC_JSON`, не печатать в трассировке и удалять в `always()` шаге. Не показывать credential в artifacts. GitHub-hosted runners эпизодические.
8. **Не путать OAuth для GitHub CI и login пользователей Android**: CI `CLASPRC_JSON` нужен для деплоя от владельца. Токены приложения/клиента — отдельная минимально привилегированная схема с проверками в GAS. Ни GitHub, ни GitHub Actions не делают частные Google Drive медиа автоматически публичными.
9. Если создание Google проекта через GitHub Action невозможно до завершения user OAuth, статус: `GITHUB_CI_READY=YES/NO`, `GITHUB_CD_WORKFLOW_READY=YES/NO`, `GITHUB_SECRET_MISSING=YES/NO`, `CLASP_LOGIN_COMPLETED=UNKNOWN/NO`, `SERVER_LIVE=NO`, `FULL_E2E=NO`. Указывать только доказанные состояния. Итоги предлагать владельцу с одной простой следующей операцией **на телефоне**, без цепочки терминальных команд.
10. Не включать примеры с настоящими OAuth токенами или кодами, ранее случайно попавшими в беседу. Старый однократный `code` считать скомпрометированным/подлежащим замене; для CI потребуется новый полностью завершённый grant либо иной официально поддерживаемый credential. Не публиковать `CLASPRC_JSON` целиком даже в «скрытом» артефакте.

## Критерий прогресса независимо от OAuth

Можно закрыть: серверный GAS код + unit/security tests, тестовый workflow, защищённый manual deployment workflow, статическую проверку манифеста, Flutter transport/две APK. **Нельзя** закрыть: фактическое создание проекта, source push, /exec, двусторонний live E2E и real media transfer, пока отсутствует подтверждённый GitHub Secret с действительным grant. Отдельной задачи №16a не делать.

## Storage bootstrap deploy gate

Deploy must not equate `clasp push` with live content storage readiness: after successful OAuth and source/version deployment, invoke protected owner-admin `storage.bootstrap` through a supported authenticated server mechanism; verify named tree and ACL in existing project root, fail closed if inherited folder permissions unsafe, record readback and schema migration in restricted report. In CI without GitHub secrets test idempotent mock Drive folder creation and catalog publish/install scenario. Never expose private owner token, user diary, root folder identifiers or grants to client/public logs. New `CONTENT_CATALOG_AND_STORAGE.md` is binding and included in predeploy gate.
