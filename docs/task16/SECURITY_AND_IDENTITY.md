# Полноценная система авторизации, доступа и хранения

1. Google identity/OAuth: исходить из уже существующего решения проекта, проверить manifest+Flutter Google sign-in; `Google ID token` проверять на доверенном сервере по подписи/JWK либо официальному verification endpoint, обязательно `aud`, `iss`, `exp`, `sub`, `email_verified` при использовании email; сервер хранит allowlist `sub` для owner/master, не сравнивает присланную роль/имя. Никогда не хардкодить пользовательские credentials и не выполнять auth через публичную строку `?token=...`. При необходимости OAuth consent — через настоящий доверенный путь, на телефоне владельца; никакого переноса auth code/refresh token в чат.
2. Client identities: публичный feed разрешать анонимно только для explicit public objects. Приватные дневники, медиа, черновики, пакеты и история скачивания принадлежат конкретному userId или allowlisted group; чтение и выдача byte-range после той же проверки ACL. Сервер `execute as owner` не означает авторское право каждого, кто знает URL.
3. Project ACL:
   - Корень проекта Google Диска `Проект Алхимик` ранее owner-only, но при создании `Хранилище Сервера Проекта Алхимик` проверять это заново и учитывать унаследованные права. Если обнаружены reader/writer/anyone inherited и закрытый root невозможен — FAIL-CLOSED + приватный альтернативный root, не публиковать дневники/аудио. Обычная папка ≠ выдача разрешения читать содержимое всем пользователям каталога.
 GAS project «Сервер Проекта Алхимик» PRIVATE owner/editor only; Root Drive folder PRIVATE. Published object может иметь public reader только по намерению автора. Не делать Google Drive `anyone: writer` ни при каких обстоятельствах; убрать публичные ссылки в приватном API. Старый «Сульфи — дневник» не изменять.
4. Grant types: owner, author/editor, subscriber/client, group, anonymous-public-read. `auth.grants` отдельная конфигурация, `revoke` немедленно прекращает новые операции, access tokens короткоживущие/проверяемые, refresh у клиентов через SDK и безопасное хранилище платформы. Тест неверной подписи, expired token, чужого aud, подменённого sub, присланной роли, replay, чужого fileId, чужого packageId, переполнения, удаления чужой записи.
5. Google Drive прямой transfer:
   - Для GAS Web App не предполагать произвольные `Authorization` HTTP headers в `e` и HTTP `206`/binary MP3 response от `ContentService`. Верифицированный ID token передавать только в защищенном POST envelope/действительно поддерживаемом auth механизме (не URL), redaction логов; для больших медиа — проверяемый JSON/base64 chunk broker с ACL per request или direct user Drive token + точечный ACL, без выдачи owner token.
 никогда не выдавать owner Drive OAuth token либо вечный Write-доступ к server root. Прямой Drive доступ разрешается ТОЛЬКО когда клиент имеет свой OAuth+точечный Drive ACL, иначе broker. Нельзя создавать «подписанный URL Drive» по аналогии с GCS: подтверждать только реально поддерживаемые механизм/ACL.
6. Keep source and credentials segregated: `ScriptProperties` для маленьких operational secrets/IDs, сам скрипт использует Google-issued owner OAuth внутри runtime там, где разрешено; ни ScriptProperties, ни OAuth secrets в отчётных ZIP. Разумные quotas и anti-abuse, rate limiting, per user/device, audit log redaction, revoke, backup.
7. Быстро проверять хеши и права, но не путать SHA с аутентификацией источника. Проверка ZIP против zip-slip/decompression bomb, MIME sniff+extension, check count/size. Не подтверждать транзакцию публикации до sha/bytes verified.
8. Для повышенной чувствительности материалов и масштабирования предусмотреть backend migration/Cloud Storage/Cloud Run как *возможную дальнейшую архитектуру*, без обязательного включения второго облака сейчас и без выдуманных обещаний Apps Script. Сейчас владелец заказал единый GAS+Drive production.
