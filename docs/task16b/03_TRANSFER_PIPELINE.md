# G2 — устойчивый контентный транспорт и подтверждение публикации
## Исходные проблемы
Upload карты модуля с тремя зависимостями и ~2.3–2.43MB медленный, 256KiB-порции, повторные `errno 7 DNS`, `Software caused connection abort`, потом требование sign-in. В очереди встречаются 0%, частичные и 100% без commit и почти одинаковые задачи. DNS/abort — признаки сетевого слоя, не факт превышения лимита GAS; проверить отдельно Google-ограничения и локальные причины.
## Инварианты
1. Queue item идентифицируется stable taskId/uploadSessionId + owner verified sub + origin contentId/revision + hash + dependency manifest + current phase, а не только отображаемым названием.
2. Состояния: LOCAL_DRAFT → QUEUED → TRANSFERRING → BYTES_ACKED → SERVER_VERIFYING → CATALOG_COMMITTED → PUBLISHED (опционально diary) и FAILED_RETRYABLE / FAILED_FINAL / PAUSED. Переходы должны быть идемпотентными; 100% bytes ≠ опубликовано.
3. Переход через любой сбой перезапуска не повреждает локальный объект. Зафиксированные сервером части/файлы повторно не отправлять без причины; подтверждать реальным authoritative server receipt/checksum, а не локальным счётчиком. Если resume backend не поддержан, сделать надежный checkpoint/reconcile и честно сообщить пределы.
4. Незавершённый манифест/зависимости недоступны клиентам. Активация каталога только после проверки всех 3 файлов по SHA, авторству, revision и ACL. Повторная попытка не создаёт новой публичной версии/обложки/дневниковой записи без намерения пользователя.
5. Cancel/withdraw/pause не удаляет пользовательский исходник и не уничтожает уже установленные клиентские медиа. Для PAUSED сохранять прогресс. Retry с bounded exponential backoff+jitter по DNS/timeout/5xx, проверять online, quota; не повторять unsafe non-idempotent POST без idempotency key.
6. Архитектуру 256KiB JSON chunks и лимит GAS измерять. Предлагать direct resumable Drive upload или другой transport ТОЛЬКО как вариант с угрозами ACL/owner-scoped grants и separate owner decision. Не выдавать клиенту прямые права к private Drive, не подключать платный сервис.
7. Проверить повторную отправку JSON/короткой дневниковой записи: причина 10-минутной блокировки на UI должна быть ясна. Нельзя ожидать 10 минут при отсутствии progress feedback и timeout policy.
8. Измерение для каждого вида: small JSON (1–4 KB), image 300–800KB, 3 real audio files ~2–5MB каждый (без копирования пользовательских исходников в публичные логи), 8–15MB synthetic file; Wi-Fi/mobile/network switch/airplane mid-chunk. Фиксировать throughput, p50/p95, retry count, avg number of GAS/Drive requests; никаких произвольных SLO без baseline, цель — подтверждённая доставляемость.
9. Exact audio revision G3: существующий fail-closed guard сохранить. НЕ делать destructive GC/миграцию в рамках 16-Б; потенциальные проблемы same-ID changed bytes отправить в отдельное решение.
