# №23 — миграции, копии и откат

## Форматы приложения

SQLite остаётся schema9. Новые исправления не добавляют таблиц/колонок и не переписывают audio/module/template IDs, frozen history, текущую конфигурацию, origins/revisions или owner scopes. Капсула остаётся существующим format/schema1. Legacy DB schema6/7/8 и капсулы schema6/7/8 принимаются существующим импортёром после проверки; новые тесты сравнивают сохранённые колонки, JSON payload и файлы.

`task23_preservation_test.dart` создаёт реальный граф тремя аудиофайлами, модулем/паузами, программой, текущей конфигурацией, завершённым checkpoint истории, офлайн-черновиком, ZIP и неизвестным файлом. Изолированные производные схем6/7/8 и актуальная9 открываются актуальным кодом дважды. Сравниваются прежние значения всех колонок, точные payload истории, IDs и SHA всех файлов. Это **fixture integration**, не Android installer gate и не материалы, созданные UI APK24 на устройстве.

Существующие тесты v1/v2/v3/v5, interrupted rollback journal, WAL и capsule legacy включены в полную регрессию. Preflight исследует производную копию до RW bootstrap оригинала. При неполной/повреждённой/неизвестной базе, недоступном media/sidecar наследстве или неоднозначном имени — отказ, сохранение исходников, без reset/GC.

## Инструмент восстановления только в отдельную копию

`scripts/task23/preservation.py` предназначен для разработчика на остановленной, явно разрешённой синтетической/следственной **копии**. Его не запускали на телефоне, личной БД или Google Drive storage. Он не внедряется в app startup.

1. Инвентаризировать все обычные файлы (включая SQLite/WAL/SHM/journal, аудио, видео, черновики, ZIP, неизвестные `.part`). Links/special paths отклоняются; оригиналы не открываются через SQLite.
2. Передать **точную доверенную локальную привязку владельца**. Это утверждение вызывающей стороны, не доказательство Google OAuth и не разрешение читать чужие записи. Нельзя извлекать право из email/имени файла или самого редактируемого manifest.
3. По умолчанию dry-run. SQLite integrity/user_version проверяются на отдельной временной производной; источник повторно хешируется. WAL не игнорируется через immutable=1.
4. Для создания диагностического snapshot в новом месте нужен явный `--write-copy`. Выходной manifestSHA хранится отдельно от snapshot как доверенный pin. Нет перезаписи даже пустой существующей папки.
5. Restore требует expected owner **и внешний SHA manifest**, проверяет имена, состав, размеры и хеши **до записи**, SQLite на производной, затем копирует только в новую независимую папку. При изменении источника — отказ, удаляется лишь новая папка этой операции; исходники остаются.
6. Результат — отдельная диагностическая копия. Она **не подменяет live app DB**, не обходит стандартный preflight/проверку ссылок приложением и не является криптографически подписанным серверным backup. Файловые права/mtime и пустые директории не являются восстановленным Android sandbox. Перед любым будущим применением нужен отдельный проверенный план.

Пример только для синтетической копии:

```text
python3 scripts/task23/preservation.py snapshot --copy-root /isolated/copy --owner synthetic-device-A --assert-copy-only
# По умолчанию только dry-run. --database db допускает старое имя только явно.
# Запись snapshot: новая --destination /isolated/new-snapshot --write-copy
# Restore: --manifest-sha256 <независимо сохранённый SHA> --owner synthetic-device-A
# Сначала без --write-copy; затем только в новую --destination /isolated/new-restore.
```

Никаких команд uninstall/clear/downgrade/import на телефоне владельца. Личные данные не переносились и не публиковались.

## Откат

До merge/deploy откат — закрыть отдельный draft PR; main/сервер/старые APK уже неизменны. На изолированной ветке возможен новый corrective commit, возвращающий код к PR54; schema/capsule wire не менялись. **Это не инструкция ставить старую APK поверх новой**. Будущий Android rollback только отдельно проверенной новой сборкой с прежней подписью и увеличенным versionCode. Не откатывать байты пользовательских файлов/SQLite из неизвестного snapshot поверх текущих.

Карантин логический, без перемещения. Цена: оставшиеся ZIP/staging занимают место. GC по одним префиксам не возвращается; будущая очистка требует доказанного владения, учёта активных задач и явного безопасного решения.
