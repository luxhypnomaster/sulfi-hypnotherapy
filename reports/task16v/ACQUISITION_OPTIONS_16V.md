# №16-В — варианты получения forensic-копии для отдельного согласования

**Это проект процедуры, не инструкция владельцу выполнять действия. Сейчас ничего на телефоне не запускаем/не устанавливаем.**

## Что проверено

Реальные APK24/25 — debug variant, debuggable в manifest, один package/cert. В disposable native CI `run-as` этого package доступен. Это подтверждает техническую возможность чтения sandbox при уже авторизованном ADB для соответствующей debug APK, но **не** наличие такого доступа на единственном телефоне владельца. Android auto-backup исключён манифестом.

## Потенциальные способы — ни один пока не утверждён для владельца

1. Уже авторизованный доверенный Android debug transport без запуска Sulfi. Считать одновременно SQLite, WAL/SHM и media tree. Сначала доказать quiescence/stability копии и невозможность перезаписи original. Наличие transport у владельца не предполагается.
2. Законный phone-only wireless-debug transport на Android11+ через доверенный локальный ADB-клиент — только после проверки OS/условий и отдельного согласия. Потребует паринга и широкого debug-доступа к устройству; не просим включать/ставить ничего сейчас. На физическом телефоне процедура ещё не доказана и не является обещанием recovery без ПК.
3. Профессиональное read-only приобретение копии при недоступности первых способов, без root/flash/reset. Никаких root/exploit/обходов защиты не предлагается.

Обычный экспорт капсулы через запуск25 сейчас не назначается: до экрана экспорта выполняется startup SQLite/cleanup; при corruption это может быть небезопасно. Установка нового диагностического Sulfi тоже не разрешена. Screenshot/сведения из уже увиденного экрана могут сузить UI-фильтр/ошибку, но не заменяют forensic bytes.

## Необходимые свойства согласованной процедуры

- Не запускать app bootstrap или сторонний recovery/reset.
- Сохранить оригинальный контекст и все файлы, не только library.sqlite; изначально зафиксировать размеры/mtime/SHA и состояние acquisition.
- При незавершённой транзакции учитывать WAL и consistency; live tar без quiescence/стабильных digest не считать атомарным snapshot.
- Приватная локальная копия по выбору владельца. Никаких реальных материалов в Git/CI/открытых отчётах. Без осознанного разрешения не просить SQLite/голос в чат.
- Анализировать производную копию; для Python-инструмента исходные DB/WAL/SHM SHA проверяются до/после, SQLite открывает только временный duplicate mode=ro.
- Recovery writes/миграцию/обновление согласовывать отдельно после доказательств и review.

Первый необходимый человеческий этап — согласовать технически допустимый доступ и snapshot, **не** переустановку или импорт. Пока этого нет, физическое восстановление владельца BLOCKED.
