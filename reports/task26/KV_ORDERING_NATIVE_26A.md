# KV: документированные гарантии и настоящий опыт ONREZA

## Что проверено

25.11.2026. Активный Git-релиз выделенного `protocol22-staging`, логически STAGING на Hobby. Настоящий HTTP-вызов `protocol22-native-probe` подтверждён журналом провайдера; `nativeReleaseBound=true`. Это не admin test-invoke с disabled/mock bindings и не локальный MemoryKV.

В отдельном уникальном ключе `synthetic26:task26:native-order:<runId>`:

1. `set` записал `{revision:2}` с TTL60; следующий `get` вернул 2.
2. `set` того же ключа записал `{revision:1}`; следующий `get` вернул 1.
3. Два последовательных `incr` отдельного счётчика вернули 1 и 2.
4. Оба ключа удалены адресно; `cleanup=true`. TTL60 дополнительно ограничивал срок.

HTTP200,2631ms. До опыта SQL подтверждена stopped/desired stopped, после опыта также stopped. В журнале маршрут относится к Function. Глобальный сон всех Compute-процессов независимо не доказан: отсутствие вызова Compute в коде и ожидание idle timeout сами по себе не являются глобальным runtime-state readback.

## Вывод о порядке

Обычный `set` **не запрещает запись меньшей прикладной ревизии поверх большей**. Проверка не доказывает все конкурентные сценарии, но прямо опровергает предположение о встроенном monotonic revision fence для этого интерфейса. Последовательные значения `incr` не доказывают глобальную атомарность или CAS.

Официальная документация runtime гарантирует read-your-writes и атомарный `incr` в пределах региона; между регионами — eventual consistency. Строгую глобальную согласованность документация относит к БД. В изученном `ctx.kv` нет подтверждённого conditional put/CAS. CLI KVv2 отдельно предлагает buffered put, `--durable` и `flush`; durability barrier не заменяет compare-and-set или version fence. Новый KVv2 Store ради исследования не создавался, его свойства не приписываются Function KVv1.

## Безопасное решение текущего этапа

`monotonicWrite=false` сохранён. Реальные HEAD/publisher не включены; нет небезопасного get+set, никакого public HEAD на основании этого опыта. SQL остаётся авторитетом. Следующий кандидат: immutable version-addressed projection с авторитетным SQL указателем либо доказанный single-writer/fencing contract. Это требует отдельного доказательства восстановления после crash/задержанной записи; не обещает Function-only/no-wake чтение текущего HEAD. Уменьшение TTL не является доказательством порядка.

Не переносить сырые provider IDs, SQL URI, токены или случайную capability в этот документ. Точные release/service/DB IDs и адрес находятся в отдельном owner-only паспорте. Подробные санитизированные события публикуются в новом комплекте доказательств №26.
